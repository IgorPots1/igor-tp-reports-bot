## 3. БЛОКИ РАБОТЫ — КОРЕНЬ и РЕШЕНИЕ

### 3.1. Качество углеводов: fast / slow / neutral / not_carb_base (`6d2a3df`, `c793961`)
- **Корень:** классификация «быстрый/медленный углевод» была у МОДЕЛИ → банан/булочка/лаваш иногда называла «медленными». Нарушение «код считает».
- **Решение:** детерминированный `classifyCarbItem(name, carbsGrams)` в `src/features/nutrition/carb-quality.ts` (порядок: грамм-гейт `CARB_CONTRIBUTOR_MIN_G=20` → fast → slow → neutral → not_carb_base; Unicode-паттерны `(?<![\p{L}])…/u`). Тег `carb_class` уходит в facts; промпт «бери класс из факта», «быстрый углевод НЕ называть „правильным источником“/„углеводной основой“», пример «крупа или паста» (рис убран из примера, НЕ из классификатора).
- **Гард `carb_quality_mismatch`** в `telegram-renderer.ts` (`validateNutritionDayProse`). **Сужен до FAST-only.**
- **УРОК #1:** изначально гард ловил и fast, и neutral → на реальной прозе дал **4/9 ложных срезов** (рис/паста — идиома «медленные»). Сузили до fast-only. → валидатор легко режет правду, проверять на реальном тексте, не только на синтетике.

### 3.2. Две тренировки в день — расход всех сессий (`63695cd`)
- **Корень:** при нескольких сессиях в день расход считался только по PRIMARY (по `WORKOUT_LOAD_PRIORITY`) → бег+силовая в один день недосчитывались.
- **Решение:** общий хелпер `sumDaySessionsExpenditureKcal<S>(sessions, estimateOne)` в `activity-energy.ts`. Применён на ОБОИХ путях: review (`methodology.ts` — `WorkoutContextByDate.sessions`, `estimateSessionEnergyKcal`) и план (`weekly-plan-formulas.ts` — сумма по `dayWorkouts`). Одиночные дни — байт-в-байт.

### 3.3. race-day мини-таблица (`a4f9628`)
- **Корень:** в `FORMULA_BY_DAY_TYPE` не было ключа `race` → таргет race-дня = null → в мини-таблице «н/д».
- **Решение:** ключ `race` (база = hard) + `computeRaceDayTarget({bodyweightKg, distanceKm, title})` — дистанция из `computeNutritionRaceProtocol` (ПМ+ → `loading.g_per_kg_high`). Валидируется на рендере → лечит сохранённые отчёты без перегенерации. Чек `check-nutrition-next-week-plan-formulas` расширен (10К/ПМ/без дистанции/без веса).

### 3.4. persist забегов (`978eba6`, ветка `fix-race-persist`)
- **Корень:** `races.json` отдаёт `student_name` + `athlete_id`, **без `student_id`-slug**. `persistScannedRaceEvents` ([tp-races-requests-once.ts]) читал `row.student_id` → `!slug` → молчаливый `continue` на ВСЕХ строках → таблица `trainingpeaks_race_events` пуста. (УРОК #4.)
- **Решение:** `buildRaceStudentResolver(students)` — резолв по `athlete_id` (парсится из `trainingpeaks_athlete_url`, числовой колонки в таблице НЕТ) → имя (только однозначное) → legacy-slug. Грузит ростер один раз; громкий warn на нерезолв + сводка `persisted N; unresolved M`. Добавлен entry-guard вокруг `main()` (модуль импорт-безопасен для диагностики).
- **Факт:** раннер ЖИВ (launchagent `com.igor.trainingpeaks-races-loop`); dry-run `15/15` резолвятся по athlete_id, 0 нерезолв; реальный `--apply` записал 15 строк; забег 20.06 «Ночной забег» виден у Нади (scan + manual сосуществуют, manual выигрывает на чтении). **Перепрогон скана больше не нужен** — мост починен, будущие сканы наполняют таблицу автоматом.

### 3.5. Юля Крылова — exclude_other для TP-«Other» (`fb59e3e` флаг, `bd0d301` фикс, ветка `fix-exclude-other-typevalueid`)
- **Корень (decisive, найден диагностикой):** TP-«Other» приходит как **`workoutTypeValueId=100` + `title="Other"` + `sportOrTypeCode=null`**. Классификатор (`workout-activity-classification.ts:124-190`) мапит по id только `3`→run, `9`→strength; токены `other/custom` ищет в `sportOrTypeCode`/снэпшоте, **не в title** → «Other» = `family:"unknown"`. Дискриминатор `isNutritionExcludedOtherActivity` (`context.ts`) смотрел только `sportOrTypeCode` (null) + `family==="other"` (unknown) → **FALSE** → её 2ч-«Other» (06-08 95мин, 06-12 120мин) доживали и по длительности читались как **«длительная»**.
- **Решение:** дискриминатор дополнен (прежние сигналы сохранены): **#2** `workoutTypeValueId===100` → excluded (надёжный якорь); **#3** сырой `title==="Other"` (точное сравнение, не подстрока), **НО** не при реальном id 3/9 (настоящий бег/силовая с тайтлом «Other» остаётся). Фильтр на ОБОИХ окнах (review+plan) — одна функция `buildNutritionTrainingPeaksWeekContext`.
- **До/после (детерминированно):** было 6 сессий + ложная длительная «Other» 1.58ч → стало 4 (только беговые), длительной нет. Чек `check-nutrition-exclude-other-activities` расширен (id=100 исключается; бег id=3 / силовая id=9 с title=Other остаются; «Brotherhood» не матчит).

### 3.6. Календарный snapping недели разбора (`be6d1cd`, ветка `fix-week-calendar-snapping`) — слой A
- **Корень (найден сравнением Туркина vs Трофимова):** `week_to` разбора = последний распарсенный день PDF (`date_range_source=parsed_pdf`). Неполный PDF (Туркина 4 дня 08-11) → `week_to=06-11` → план = `review_to+1..+7` = **06-12..06-18**, сдвинут на 3 дня назад → не дотягивает до текущей недели. Полный PDF (Трофимова 08-14) → план 15-21, корректно. Отличие — только полнота PDF.
- **Решение (слой A):** `snapParsedDatesToCalendarWeek(dates)` в `report-date-coverage.ts` — снап к полной календарной неделе (пн–вс) по **большинству** распарсенных дней (ничья → ранняя неделя). Снап в `resolveNutritionEffectiveReportWeek` (интейк-тайм, **не ретроактивно** — старые отчёты не переписываются). mismatch-нотис показывает **СЫРЫЕ** даты PDF (не снапнутые). Данные не выдумываются — разбор по реально распарсенным дням.
- **До/после:** Туркина 08-11 → **08-14** (при перезаливе) → план 15-21; Трофимова 08-14 → **08-14** (байт-в-байт). Весь nutrition-сьют PASS 70/0.

### 3.7. Снятие hard-блока безопасности (`ea63ab2` → `b696d66` → `a85ebc4`)
- **КОНТЕКСТ РЕШЕНИЯ (осознанное решение Игоря, обсуждено с ученицами — НЕ баг, не возвращать):** снятие hard-БЛОКА продумано и проговорено с ученицами. Логика: блок чаще срабатывает на **НЕПОЛНОМ логировании** (записано не всё съеденное), а не на реальном голодании; стена в этом случае мешает дать обратную связь — основную ценность системы. Снят именно **БЛОК (стена)**, а **сигналы/пометки ОСТАЮТСЯ**. **EA-пол и методика lose НЕ тронуты.** Human-in-the-loop сохранён: реально критичную ситуацию Игорь видит в пометках и направляет ученика к врачу — система не замена клинической оценки, а инструмент обратной связи. Семешина (5 дней <1300, EA красная) теперь получает разбор с честной пометкой «критически мало, повторять нельзя», а не блок — это **ожидаемо и by design** после этого решения.
- **Решение Игоря:** все ученики адекватны; низкоэнергетические дни разбираем как обычно с честной пометкой «критически мало, повторять нельзя»; клинические сигналы — «как у всех»; кнопку override убрать. Принципы генерации не менять.
- **Три захода (почему):** (1) `ea63ab2` — `buildNutritionSafetyFlags`: `blocked=false`, `doNotSendReasons=[]`. Не помогло — блок реконструировался из `hard_flags` → `manual_review_required:*` в 5 местах. (2) `b696d66` — `hard_flags=[]` в источнике (сигналы → `softFlags`). Не помогло для СТАРЫХ сохранённых строк. (3) `a85ebc4` — гейт combine (`isReviewBlockedSafety`/`isPlanBlockedSafety`) ИГНОРИРУЕТ safety-блок (`isSafetyDerivedReason` = `startsWith("manual_review_required:")`) → старые строки разблокируются на рендере без перегенерации. **EA-пол и методику lose не обходим — снят только hard-БЛОК (сигналы остаются пометками).**

### 3.8. Имена продуктов / приветствие (`3438a65`), крупа-паста (`c793961`), Table Tennis (`090db95`) — кратко
