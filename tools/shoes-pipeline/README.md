# Конвейер сбора базы кроссовок

Этап 1 к подборщику (`/tools/shoes`). Собирает характеристики моделей из
внешних источников, сверяет их между собой и складывает в каталог по схеме
приложения.

Это конвейер, а не наполнение: данные тут не пишутся руками. Поле, которого
нет в источнике, остаётся пустым и уезжает в отчёт о пропусках. Правдоподобное
число вместо пустого — брак, а не результат.

## Порядок запуска

```
# 1. Гейт: условия использования источников. Без него загрузчик не работает.
npx tsx tools/shoes-pipeline/audit-sources.ts

# 2. Сбор. Только у источников со статусом allowed, с паузами и кэшем.
npx tsx tools/shoes-pipeline/collect.ts --limit 80
npx tsx tools/shoes-pipeline/collect.ts --all

# 3. Сборка каталога-кандидата и прогон через валидатор приложения.
npx tsx tools/shoes-pipeline/build-catalog.ts

# Правила сверки и порогов — без сети.
npm run check:shoes-pipeline-rules
npm run typecheck:shoes-pipeline
```

## Устройство

| Файл | Что делает |
|---|---|
| `lib/sources.ts` | реестр источников — он же гейт: статус ≠ `allowed` означает, что страницы не скачиваются |
| `lib/robots.ts` | разбор robots.txt: группы, Allow/Disallow, победа самого длинного правила, `*` и `$` |
| `lib/fetch.ts` | загрузчик: спрашивает гейт, уважает robots и Crawl-delay, держит паузу на хост, кэширует на диск |
| `lib/parsers/rtings.ts` | разбор страницы обзора: значения плюс кусок страницы, по которому их можно проверить |
| `lib/reconcile.ts` | сверка: нет источника — не берём, один источник — мало, расхождение > 10 % — в отчёт |
| `lib/tiers.ts` | пороги уровней по распределению собранных цен (терцили), а не на глаз |
| `lib/schema-map.ts` | карта «поле схемы → чем закрывается» |
| `audit-sources.ts` | гейт раздела 4 |
| `collect.ts` | проходы 1–3 |
| `build-catalog.ts` | сборка кандидата + валидация валидатором приложения |

Кэш страниц — `tools/shoes-pipeline/.cache/` (в git не идёт). Он же
доказательство: любое число в базе прослеживается до сохранённой страницы.

## Правила, которые конвейер держит

- **Поле без источника в базу не попадает.** Происхождение каждого поля лежит
  рядом, в `reports/catalog.provenance.json`: источник, вид (замер или
  заявленное) и кусок страницы.
- **Числовое поле требует двух независимых источников.** Одного мало — поле
  остаётся пустым, а в отчёте видно, чего не хватило.
- **Расхождение больше 10 % не усредняется.** Среднее между 39 и 45 даёт 42 —
  число, которого нет ни в одном источнике, зато выглядит достоверно.
  Расхождение почти всегда значит, что источники говорят о разных вещах:
  заявленное против измеренного, мужская версия против женской, обновлённая
  модель против прошлогодней. Разбирает человек.
- **Замер важнее заявленного.** Там, где источники сошлись, в базу идёт
  измеренное значение.
- **Валидатор — тот же, что у приложения.** `build-catalog.ts` импортирует
  `validateCatalog` из `src/features/shoes/schema.ts`, а не свою копию:
  разойтись они не смогут.

## Происхождение полей: сайдкар, а не расширение схемы

Наряд требует ссылку на источник у каждого поля. Схема приложения хранит
`sources` на всю запись. Расширять её молча нельзя — новое поле означает
второй проход по всем источникам, — поэтому происхождение по полям лежит
отдельным файлом `catalog.provenance.json`, а в каталог уходит список
источников записи. Схема приложения не тронута.
