# Задача 3 — лента по времени (ветка feature/club-feed-time-sort)

## 3.1 Текущая сортировка — найдена
`loadFeedCandidates` (service.ts): `order(workout_date desc).order(id desc)`, курсор `date|id`. `id` —
это **random UUID v4**, не порядок вставки → внутри дня порядок фактически случайный (даже «хуже», чем
по вставке). Подтверждено миграцией создания таблицы (`id uuid default gen_random_uuid()`).

## 3.2 Новая сортировка — (feed_ts desc, id desc)
`feed_ts = coalesce(start_time, workout_date::text)` — генерируемая колонка (миграция 20260905).
ФАКТ по данным: `start_time` = полный наивно-локальный ISO «2026-08-04T07:47:23» (префикс = workout_date),
null ~0.75% (146/19422), суффиксов «Z» нет → лексикографический порядок = хронологический.
**ФОЛБЭК для строк без start_time (моё решение):** feed_ts = workout_date → такие тренировки падают в
НИЗ своего дня (после всех, у кого время есть). Причина: нет зафиксированного времени = меньше всего
уверенности в позиции; безопаснее внизу дня, а не наверху. Доля мала (0.75%).

## 3.3 Keyset-пагинация — курсор на тех же полях, проверено фактом
Курсор `feed_ts|id` (оба поля НЕПУСТЫЕ → нет NULL-краёв, где обычно и появляются дубли/пропуски).
`.or(feed_ts.lt.X, and(feed_ts.eq.X, id.lt.Y))`. **Симуляция на реальных данных:** 2528 кандидатов в
окне 45 дней, keyset собрал ровно 2528, **дублей 0, потерь 0, порядок === эталон**. Листание не теряет
и не двоит.

## 3.4 Индекс + замер
Добавлен `club_cache_feed_ts_idx (feed_ts desc, id desc) where is_completed=true` — ровно под ORDER BY
+ SQL-фильтр ленты (index scan вместо sort). **Замер «до»:** 143 мс/запрос (5 прогонов). «После» —
померить после применения миграции (индекс должен убрать сортировку; ожидаю ≤ 143 мс). До применения
код работает на ФОЛБЭК-пути (старый порядок) — feed не ломается (smoke-club [feed] зелёный).

## 3.5 Опоздавшая загрузка — встаёт по времени старта, не наверх
Лента сортируется по feed_ts (время старта), а не по вставке/scanned_at. Тренировка, залитая с
опозданием, но со своим start_time, встаёт на своё место по времени. Подтверждено конструкцией и
примером дня (10:59 → 09:45 → … по времени).

## Deploy-before-migrate
`loadFeedCandidates` при отсутствии колонки feed_ts (миграция ещё не применена) падает на старый путь
(workout_date desc, id desc) — тем же курсором (feed_ts ≡ workout_date, работает по префиксу-дате).
Feed не ломается ни на секунду. Проверено: smoke-club [feed] зелёный на живой БД без миграции.
