# Разведка: перенос тренировок без мака

**Дата:** 2026-07-14 · **Режим:** read-only, код исполнения не менялся · **Ветка:** `feature/move-recall-and-multi`

Вопрос Игоря: `tp-actions-loop --execute-real` крутится на его маке. Уснул мак — переносы встали.
Можно ли перенести исполнение в облако, и как туда доставлять токен.

Это **чертёж, не реализация**. `inspectActionCalendar` (браузер-предохранитель) по решению Игоря
**не снимается** — обсуждается отдельно, после разведки.

---

## 1. Главный факт: мутация УЖЕ идёт без браузера, и уже в проде

Безбраузерный путь переноса не гипотеза — он **работает на боевых учениках прямо сейчас**.

Реальный перенос Надежды Семершиной 14.07.2026:

```
trainingpeaks_action_runs, 2026-07-14 19:09:01+00
  run_type      = real
  status        = completed
  dry_run       = false
  executed_via  = "http_live_primary"     ← ни одного клика в браузере
  runner_id     = tp-actions-once:local-mac
```

`TP_MOVE_RESOLVER_MODE=live_primary` лежит в `.env` репозитория, а `tp-actions-loop` подхватывает
`.env` из папки репо ([tp-actions-loop.ts:148](../tools/trainingpeaks-export/scripts/tp-actions-loop.ts#L148)) —
хотя launchd-плист эту переменную не задаёт. То есть режим включён «через `.env`», а не через плист.
**Это стоит зафиксировать явно** (см. §5): сейчас прод зависит от файла, про который плист ничего не знает.

Сама мутация — обычный HTTPS:

```
PUT https://tpapi.trainingpeaks.com/fitness/v6/athletes/{athleteId}/workouts/{workoutId}
Authorization: Bearer <token>
```

`putWorkout` — это `fetch()` ([tp-api-client.ts:291](../src/features/trainingpeaks/tp-api-client.ts#L291)).
В `src/` **нет ни одного импорта Playwright**. Playwright — зависимость только подпроекта `tools/`.

Записи в TP под bearer-токеном доказаны вживую ещё 12.07 (наряд `2026-07-12-2300-tp-api-pr4-live-writes`):
create / update / delete / strength + откат, на тестовом атлете 3102415, `docs/tp-api-capability-matrix.md`.
**Нового проба не требуется — это установленный факт, а не предположение.**

---

## 2. Что РЕАЛЬНО держит перенос на маке

Ровно две вещи. Ни одна из них не «наследие Playwright».

### 2.1 Браузер-предохранитель `inspectActionCalendar` — НЕ ТРОГАЕМ

[tp-actions-once.ts:8393](../tools/trainingpeaks-export/scripts/tp-actions-once.ts#L8393), вызов на
[:9775](../tools/trainingpeaks-export/scripts/tp-actions-once.ts#L9775). Поднимает Chromium
**безусловно, ДО** развилки режима. Комментарий в коде на [:9976](../tools/trainingpeaks-export/scripts/tp-actions-once.ts#L9976)
говорит прямо: режим гейтит только то, чем ВЫПОЛНЯЕТСЯ мутация, а браузерная проверка личности и
ревалидация кандидата «уже отработали, безусловно, независимо от режима».

Что он делает: DOM-проверка, что мы в календаре **того самого** ученика, и переподтверждение
кандидата-тренировки перед записью. Это предохранитель против переноса чужой тренировки.

`live_primary` убирает **вторую** браузерную сессию (resolve + PUT), а не первую.

**Статус: по решению Игоря не снимаем.** Замена его на HTTP-эквивалент — отдельное решение,
и разговор про него должен опираться на данные, а не на удобство. Данные, которые есть:
shadow-бэкфилл 13.07 воспроизвёл 58 из 61 переноса HTTP-резолвером, 0 ошибок сопоставления id,
5 корректных отказов. Данных, которых **нет**: таблица `trainingpeaks_move_shadow_comparisons`
в проде **пуста (0 строк)** — то есть постоянного теневого сравнения сейчас не ведётся,
бэкфилл был разовым прогоном скрипта.

### 2.2 Токен: единственный источник — профиль Chromium на маке

```
профиль Chromium (tools/trainingpeaks-export/.playwright-profile/trainingpeaks, ~858 МБ, непереносим)
  → кука Production_tpAuth
  → ~/.tp-reports-bot/session-snapshot.json   (atomic write, chmod 0600)
  → GET tpapi/users/v3/token  с этой кукой
  → bearer access_token (в памяти, refresh по expires_in с запасом 60 с)
```

- TTL куки — **~30 дней** (`docs/tp-api-capability-matrix.md:89`).
- Снапшот-файл — **уже спроектированный шов переносимости**: его читает чистый `fetch`, без Playwright.
- Админки / API-роута / таблицы, куда можно **вставить куку руками**, — **не существует**
  (грепал `src/app/` по `Production_tpAuth|bearer|session-snapshot` — ноль совпадений).
- `TRAININGPEAKS_API_BEARER` — **не тот путь**: легаси, read-only проб-скрипты, к переносам отношения не имеет.
- Прошлый дизайн **сознательно отверг** сырую куку в переменной окружения
  (`capability-matrix.md:116`: «никакой сырой секрет не лежит в env»).

## 3. Варианты доставки токена в облако

Игорь готов **раз в месяц обновлять доступ руками** — это ключевое ограничение, оно совпадает с TTL куки.

### A. Админ-форма → зашифрованная строка в БД → облачный раннер читает

Игорь раз в 30 дней логинится в TrainingPeaks в обычном браузере, копирует куку `Production_tpAuth`,
вставляет в форму в админке. Строка шифруется и кладётся в таблицу; облачный раннер читает её вместо
файла-снапшота.

- **+** Ровно ложится на «раз в месяц руками». Мак не нужен вообще.
- **+** Ротация видима и логируема (кто, когда, до какого числа валидно).
- **+** Не нарушает старый принцип «сырой секрет не в env» — секрет в шифрованном хранилище, не в переменной.
- **−** Надо написать: роут + форму + шифрование + таблицу. Самый большой объём работы.
- **−** Достать куку из браузера руками — операция для человека неприятная (DevTools → Application → Cookies).

### B. Кука в секрет облака (env / secret store)

- **+** Почти нулевая работа.
- **−** Прямо противоречит явному решению прошлого дизайна. Сырой секрет в переменной окружения.
- **−** Ротация = редеплой. Раз в месяц дёргать деплой ради куки — так себе.

### C. Мак остаётся только «обновлятором токена», переносы — в облаке

Мак раз в 30 дней (или по крону раз в сутки, что дешевле и надёжнее) поднимает Chromium, обновляет
куку, **пушит снапшот в облако** (в ту же зашифрованную таблицу). Исполнение переносов живёт в облаке.

- **+** Никакого ручного копирования куки — мак делает то, что уже умеет.
- **+** Мак может спать: если он проснётся хотя бы раз в 30 дней, всё живо. Уснувший на неделю мак
  больше не блокирует переносы — а это ровно исходная боль.
- **+** Переиспользует `tp-refresh-session-snapshot.ts`, который уже написан и работает.
- **−** Мак всё ещё в цепочке (но не в критическом пути каждого переноса).
- **−** Нужен канал «мак → облако» (тот же зашифрованный стор, что и в A).

### Рекомендация

**C, с прицелом на A как запасной ход.** У C и A общий фундамент — зашифрованное хранилище токена в БД;
C добавляет к нему автоматический пуш с мака, A — ручную форму. Сделать сначала хранилище, потом C;
форма из A становится аварийным рычагом на случай, когда мак недоступен дольше 30 дней (например,
Игорь надолго уехал без него).

Это НЕ снимает браузер из §2.1 — он остаётся, и пока он остаётся, переносы в облако не уедут.
Порядок работ поэтому такой: **сначала решение по предохранителю, потом токен**. Токен без снятия
предохранителя не даёт облака; предохранитель без токена — тоже. Но решение по предохранителю — риск,
а токен — просто работа, поэтому обсуждать надо сначала риск.

## 5. Что стоит починить независимо от облака

1. **`TP_MOVE_RESOLVER_MODE` живёт в `.env`, а плист про него не знает.** Прод сейчас исполняет
   переносы через `http_live_primary` — но только потому, что `tp-actions-loop` читает `.env` из
   папки репо. Любой, кто пересоздаст плист «по инструкции», молча откатит прод на DOM-путь и не
   заметит. Либо задать переменную в плисте явно, либо поменять дефолт в коде.
2. **`trainingpeaks_move_shadow_comparisons` пуста (0 строк).** Механизм теневого сравнения есть,
   но не пишет. Если планируется снимать браузер-предохранитель — это ровно тот прибор, который
   должен набрать статистику ДО решения. Сейчас решение опиралось бы на разовый бэкфилл 13.07.

## Итог

- Мутация переноса **уже** идёт по HTTP с bearer-токеном, без браузера, **в проде, на живых учениках**.
- Переносы держат на маке **две** вещи: браузерный предохранитель (не снимаем — решение Игоря) и
  источник куки.
- Токен в облако: рекомендую зашифрованное хранилище в БД + автопуш снапшота с мака (вариант C),
  с ручной админ-формой (вариант A) как аварийным рычагом.
- Порядок: сначала решение по предохранителю (это риск), потом токен (это работа).
