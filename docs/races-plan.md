# Старты и выходные → пайплайн мутаций TP (план, НЕ реализация)

Дата: 2026-07-25. Блоки 6 и 8. Здесь только описание маршрута; сама мутация TP в этих нарядах НЕ реализуется.

## 1. Как подтверждённый старт поедет в TP

Ученик из мини-аппа только ЗАЯВЛЯЕТ старт → строка в `club_races` со `status='declared'`. В TP ученик не пишет. Дальше — существующий тренерский пайплайн мутаций (тот же, что для move-workout / zone-apply):

1. **Очередь на подтверждение.** Тренер видит заявки (панель club-admin, отдельный наряд) и подтверждает: `declared → approved` (`approved_by`, `approved_at`).
2. **Dry-run.** Подтверждённый старт превращается в TP-действие (создать событие/гонку в календаре атлета на `race_date`) и прогоняется в prepare-only/dry-run — как остальные TP-мутации (см. `action-dry-run-telegram-copy.ts`, `tp-actions-once`). Фингерпринт, проверка дат, confidence-гейт — как есть, не ослабляются.
3. **Подтверждение исполнения → очередь.** Тренер подтверждает dry-run → действие уходит в очередь исполнения (`tp-actions-execute-once`).
4. **Локальный раннер.** Mac-runner исполняет запись в TP под гардами (человеческое подтверждение, source-date, конфиденс). `status: approved → synced_to_tp`, `sync_result_ref` = ссылка/id результата.
5. **Верификация.** Пост-проверка, что событие в TP создано корректно (как verify-first в остальных мутациях).

Ключевое: мини-апп — только источник заявки; ни одна ступень записи в TP не инициируется учеником.

## 2. Почему старты — кандидат на ПАКЕТНОЕ подтверждение

Старты приходят пачками (клуб бежит один забег; сезонный календарь). Каждый — однотипное действие «создать событие на дату». Поэтому в панели тренера логично не по одному, а списком: выбрать N заявок → один dry-run пакетом → одно подтверждение → очередь. Это снижает клики и риск пропустить. Реализация пакетного подтверждения статуса — в наряде club-admin (раздел 1), исполнение в TP — позже.

## 3. Что дата старта ОТКРЫВАЕТ в Supabase (связи)

Дата старта — это якорь, от которого считаются другие слои (всё read-only/подсказки, без автозаписи):

- **Предстартовые интервалы.** Окно `race − 6 … − 3` дня → приоритет лёгких/поддерживающих тренировок (taper). Связка с `trainingpeaks_workout_cache` (плановые тренировки в этом окне) для подсветки «что должно стоять».
- **Предстартовое питание.** Дни `race − 3 … 0` → углеводная загрузка / режим (модуль nutrition уже считает по длинным; дата старта даёт явный триггер).
- **Taper-слой E-Predictor.** Прогноз результата (`getClubPrediction`) активируется именно при объявленном старте, на его дистанцию (Блок 7.3). Дата → пересчёт по мере приближения.
- **Будущий поиск протокола.** После даты старта — фаззи-матч по фамилии на probeg.org → официальный результат. При совпадении апгрейд рекорда: `club_records.source: reconstructed → official_protocol` (+ `protocol_url`, `protocol_matched_at`). Поля уже заложены в `club_races` и `club_records`. Это перекроет реконструированный результат официальным (precedence: coach_confirmed > official_protocol > reconstructed).

## 4. Выходные (Блок 8) — тот же маршрут

Ученик ЗАЯВЛЯЕТ выходной → `club_dayoff_requests` со `status='pending'`. Не проставляет сам, в TP не пишет, уведомлений нет.

1. Тренер в очереди: `pending → approved | rejected` (`status_by`, `status_at`).
2. Подтверждённый выходной → TP-действие (пометить день(и) как day-off / снять плановые) через тот же dry-run → confirm → очередь → раннер → verify. `status: approved → applied`, `apply_result_ref`.
3. Пакетное подтверждение так же уместно (несколько учеников/дней списком).

Автоприменения и автоотправки нет ни на одной ступени; всё через тренерское подтверждение.

## 5. Что НЕ делается в этих нарядах
- Никакой записи в TP из мини-аппа.
- Никакого исполнения мутаций (только заявки + статусы в Supabase).
- Пакетное подтверждение и исполнение — наряд club-admin и последующий.
