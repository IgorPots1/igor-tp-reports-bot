# TP race_events - как наполняется и добор прошлого

Дата: 2026-07-29. Только чтение/код-разведка. Ничего не запускал, в БД/TP не писал.
Контекст: прошлые забеги, отмеченные в TrainingPeaks, в систему не попадают. Разбор по коду.

## 1. Как наполняется `trainingpeaks_race_events` (факт по коду)

Цепочка:
1. **enqueue** - `tools/trainingpeaks-export/scripts/enqueue-race-scan-weekly.ts` (launchd,
   еженедельно) вставляет job `trainingpeaks_jobs(job_type='race_scan_events')` с окном
   `week_from = belgradeToday()`, `week_to = today + FORWARD_DAYS` (**дефолт 120 дней**,
   стр. 90–101). **Окно ТОЛЬКО ВПЕРЁД** - имя `FORWARD_DAYS`, `from = сегодня`.
2. **claim/loop** - `tp-races-requests-once.ts` берёт queued job и вызывает
   `tp-scan-events --from=week_from --to=week_to` (стр. 517).
3. **worker** - `tp-scan-events.ts` (playwright) ходит в TP API
   `GET https://tpapi.trainingpeaks.com/fitness/v6/athletes/{athleteId}/events/{from}/{to}`
   по каждому атлету, извлекает `event_title`, `distance`, `goalValue`(цель) → пишет `race_events`.

**Вывод:** сканер **forward-only**. `race_events` содержит только будущие гонки в окне
`сегодня .. +120 дней`. Прошедшие гонки не собираются - как только дата гонки уходит в
прошлое, новые запуски её окном не покрывают. Отсюда: прошлые забеги в систему не попадают.

## 2. Счётчики (нужен прогон - скрипт `audit-club-race-events-coverage`)

Из песочницы БД недоступна (креды у Игоря). Скрипт (read-only) посчитает: всего записей,
период (min/max event_date), сколько прошлых vs будущих (относительно сегодня), у скольких
атлетов, провал в истории. Запуск: `npm run audit-club-race-events-coverage`.

## 3. Добор прошлых гонок из TP - ВОЗМОЖЕН, воркер уже умеет

`tp-scan-events` принимает **произвольное окно** `--from=YYYY-MM-DD --to=YYYY-MM-DD`
(стр. 219–267) - forward-only живёт только в enqueue, не в воркере. Значит добор прошлого =
запуск воркера с прошлым окном, тот же эндпоинт.

**Оценка объёма/времени:** playwright-скан по ~113 атлетам, TP events-эндпоинт принимает
диапазон `{from}/{to}` целиком (не по неделям в самом запросе - окно передаётся как есть).
Многолетнее окно на атлета = один запрос диапазона, но по всем атлетам последовательно с
TP-сессией → минуты-десятки минут, зависит от истории. Разумно бить на годовые окна.

**Команда (НЕ запускал - твоя рука), из `tools/trainingpeaks-export`:**
```bash
cd /Users/igor/igor-tp-reports-bot/tools/trainingpeaks-export
# прошлое окно, напр. последние 3 года до вчера:
npm run tp-scan-events -- --from=2022-07-01 --to=2026-07-28
```
Идемпотентность: запись в `race_events` - upsert по (атлет, дата, событие) в существующем
воркере; повтор не задвоит. Начни с узкого окна (напр. один прошлый год) для проверки объёма,
потом расширяй. Дедуп против уже существующих будущих записей - по тому же ключу.

## 4. Как TP помечает прошедшую гонку с результатом (факт по коду)

Прошедшая гонка в TP - это **EVENT** (тот же events-эндпоинт), несущий `event_title`, дату,
`distance`, `goalValue` (**цель** времени). **Само событие финишный результат НЕ несёт.**
Реальный результат (время финиша) - в **завершённой тренировке той же даты**; связка
«событие ↔ тренировка» и вывод результата - уже в `tp-probe-race-results.ts`
(`result_status: probable_result | possible_result` + confidence-скор). То есть прошлые
гонки лежат как Events, а не как «обычные тренировки с признаком гонки»; результат берётся
из парной тренировки, а не из события.

**Следствие для системы:** добрав прошлые Events (п.3), мы получим ДАТЫ+НАЗВАНИЯ+ДИСТАНЦИИ
прошлых гонок. Результат по каждой уже реконструируется из тренировки того дня
(classifyRecordType + records). Это и есть путь «больше гонок без сопоставления атлетов»:
не импорт из Run Club, а расширение окна собственного TP-сканера в прошлое.

## Вердикт (Part B)
Сканер forward-only - это и есть причина. Воркер уже умеет прошлое окно; добор прошлых гонок
из TP реален и дёшев (та же инфраструктура, команда выше), и даёт гонки БЕЗ рискованного
сопоставления атлетов Run Club. Рекомендую сделать это ПЕРЕД импортом Run Club.
