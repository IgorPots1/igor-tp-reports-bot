### Строки / БД против JS (п.0)
Отдельного счётчика «мс в БД vs мс в JS» не ставил, но природа путей и один эксперимент дают однозначный вывод:
- **Доминирует чтение из БД, не JS.** Доказательство: профиль упал 6120→409 **только** от сужения ЧТЕНИЯ (365 дней по всем ученикам → 365 дней по своему + текущая неделя по всем). JS-агрегация не менялась. То есть ~94% времени профиля было в чтении широкого окна, а не в вычислениях.
- Горячий путь всех невматериализованных вкладок — `loadClubWorkoutRows({from,to})`: пагинированное чтение `trainingpeaks_workout_cache` за окно по ВСЕМ ученикам (лента 45д, статистика ~14д, топы 60д, челлендж ~40д). Окно клуба — тысячи–десятки тысяч строк; каждая классифицируется в JS.
- Records/профиль-рекорды в БД читают только маленькие снапшоты (`club_record_snapshots`), поэтому 385/369 ms — это «пол» (loadClubStudents + снапшоты + coach + freshness).

## Что сделано (п.1, 2, 3, 5) — закоммичено, проверено

**П.1 Профиль на снапшоты (коммит 73f38bf).** `getClubProfileDetail` больше НЕ делает живую реконструкцию рекордов (убраны `loadOrderedLaps` + `loadWorkoutQualityIndex` из профиля) и не читает 365д по всем. Рекорды идут через новый общий `personalRecordsFromSnapshots(studentId, snapshots, coach)` — **тот же источник, что вкладка «Результаты»** (getClubRecords теперь зовёт ту же функцию с теми же аргументами) → совпадение гарантировано кодом, не совпадением расчётов. Объёмы/серии/типы — узкое 365д чтение только своего ученика; ранг челленджа — чтение всех, но только за текущую неделю.
Примечание: `getClubPublicProfile` (Фаза 5) и `getClubPrediction` (Фаза 9) ещё используют живую реконструкцию — они вне Фазы 1 и за флагами.

**П.2 Лента — keyset в Postgres (73f38bf).** Вместо «загрузить 45 дней по всему клубу и резать в памяти» — `loadFeedCandidates`: фильтр по дате + `is_completed` + сортировка `(workout_date,id) DESC` + `LIMIT` на стороне БД; курсор keyset `"<workout_date>|<id>"` (без offset-дрейфа). Классификация «бег/видимость» зависит от classify-логики, не от колонки, → JS-постфильтр на ограниченной пачке, поэтому over-fetch ×4 до заполнения страницы. `hasMore` — редкий ложный «показать ещё» максимум даёт одну пустую подгрузку (UI показывает «это всё»).

**П.3 Индекс-выровненный порядок (73f38bf + миграция).** Все оконные чтения теперь `.order(workout_date).order(id)` вместо `.order(id)` (не совпадал ни с одним индексом → полная сортировка). Миграция-файл `supabase/migrations/20260730000000_club_cache_date_id_index.sql` добавляет `club_cache_date_id_idx (workout_date ASC, id ASC)`. **НЕ применена** (миграции — только файлами). EXPLAIN-команда до/после — в комментарии миграции.
⚠️ Замеры «ПОСЛЕ» для оконных вкладок (лента/статистика/топы/челлендж) сделаны БЕЗ применённого индекса — после применения они станут ещё быстрее (уходит полная сортировка окна).

**П.5 Индикатор свежести снапшотов (коммит 423ee53).** `/admin/club/manage` показывает «Пересчёт Результатов = N назад» + красный баннер, если >24ч или пусто. Источник — `MAX(computed_at)` из `club_record_snapshots`.

## П.5 факт: где вшит пересчёт
`materializeClubRecords` вызывается ТОЛЬКО из CLI `scripts/materialize-club-records.ts`, который запускается из двух скан-скриптов:
- `tools/trainingpeaks-export/scripts/run-workout-cache-scan.sh:29-31`
- `tools/trainingpeaks-export/scripts/run-fit-ingest-scan.sh:69-71`

Оба **гейтятся `CLUB_MATERIALIZE_ENABLED=true` (default false)**. Если на Mac-раннере (launchd) флаг не выставлен — пересчёт НЕ идёт, снапшоты замирают, «Результаты» устаревают молча. Проверить фактом со стороны раннера я не могу (это локальное окружение launchd, .env недоступен из песочницы). Индикатор в админке теперь это ловит. **ДЕЙСТВИЕ ИГОРЮ: убедиться, что `CLUB_MATERIALIZE_ENABLED=true` в окружении сканов.**

## Что НЕ сделано и почему (п.4 — агрегаты)
**Статус: спроектировано, не реализовано.** Это самый крупный и чувствительный к корректности кусок; при неверной реализации ученикам уйдут неправильные числа лидербордов. Не стал впихивать непроверенную таблицу + RLS в high-risk репозиторий на хвосте длинной сессии. Дизайн — ниже; это следующая группа коммитов Фазы 1.

Дизайн `club_daily_aggregates` (миграция-файлом):
- Колонки: `student_id uuid, day date, running_km numeric, running_count int, planned_running int, completed_running int` (+ `computed_at`), PK `(student_id, day)`. Дневная гранулярность (не недельная), т.к. серии (streak) и «активные дни» требуют дней.
- Материализация: в том же `materializeClubRecords`-проходе (или рядом), инкрементально по `loadStudentsTouchedSince`; DELETE+INSERT по (student, окно).
- Потребители переводятся на агрегаты:
  - `getClubStatistics`: клубный км тек/пред неделя, активные, тренировки, W/W — сумма дневных по неделям.
  - `getClubChallenge`: `computeAutoGoalKm` (5 недель клубного км) и вклад — суммы дневных, без 5 полных проходов сырого окна.
  - `getClubExtendedTops`: byVolume/byCount/byCompletion — суммы; byStreak — из «активных дней».
  - Ранг в профиле — уже сужен (текущая неделя), можно тоже из агрегатов.
- Риск корректности: `buildWeekPerformers`/`computeAutoGoalKm`/streak-grace нужно воспроизвести из агрегатов ТОЧНО. Требует сверки чисел до/после на реальных данных (как сделано для рекордов в Фазе 1.1).
- Ожидаемый эффект: топы 1118→сотни мс, челлендж/статистика — аналогично.

## Итог целям
- Профиль, результаты, лента — сотни мс (цель достигнута; лента ещё улучшится с индексом).
- Топы/челлендж/статистика — 0.4–1.1с; в целевые «сотни мс» их выводит п.4 (агрегаты). Что мешает: чтение широкого окна по ВСЕМ ученикам на каждый запрос.
