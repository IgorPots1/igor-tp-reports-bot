# Пожелания учеников как вход планировщика — инвентаризация

Замер 13.08.2026, READ-ONLY. Отвечает на один вопрос: **чем реально можно кормить
планировщик сегодня, а чего нет.**

## Короткий ответ

**Автоматически — ничем.** Ни одного машиночитаемого пожелания в базе не существует.
Материал есть и он неплохой, но это проза, извлечённая моделью из переписки и не
подтверждённая тренером. Пускать её прямо в форму недели нельзя: неверное извлечение
испортит неделю молча.

## 1. club_dayoff_requests — просьбы о выходном

| что | факт |
|---|---|
| строк в таблице | **0 за всё время** |
| таблица | есть (миграция `20260725150100`), RLS и гранты на месте |
| API мини-аппа | есть — `src/app/api/m/club/dayoff/route.ts` |
| экран ученика | есть — `/m/club`, вкладка «Выходные» |
| очередь тренера | есть — `/admin/club/queue` |
| **почему ноль** | **за флагом `CLUB_DAYOFF_ENABLED`, которого в `.env.local` нет.** Геттер возвращает false, маршрут отдаёт 503. |

То есть intake **написан целиком и выключен одной строкой**. Это не «нужно разработать» —
это «нужно включить и посмотреть, пойдут ли строки».

Важно про смысл: ученик ЗАПРАШИВАЕТ выходной, тренер подтверждает, и только потом
изменение уезжает в TP через его же конвейер. Мини-апп в TP не пишет никогда.

## 2. trainingpeaks_student_memory_items — факты об ученике

1477 строк, 110 учеников. Ключ `student_id` — это **`trainingpeaks_students.id` (UUID)**,
а НЕ слаг `student_id`. Совпадение 110 из 110 по UUID, 0 по слагу.

Типы:

| тип | строк |
|---|---|
| health_status | 307 |
| **schedule_constraint** | **203** |
| load_tolerance | 196 |
| emotional_state | 166 |
| pain_or_injury | 159 |
| race_or_goal | 140 |
| equipment_or_device_note | 106 |
| travel_or_life_event | 89 |
| **availability_preference** | **58** |
| **planning_preference** | **53** |

Релевантных типов (три выделенных) — **314 строк, из них активных 167**.
`valid_until` проставлен у 153 из 314. Доверие от 0.7 до 1.0. Источник — `ai_extraction`.

### Колонка `structured` заполнена, но пуста по сути

Непустой `structured` у 313 из 314 релевантных строк — то есть формально 100%.
Внутри **всегда одно и то же**: `{"note": "свободный текст"}`. Иногда добавляется
`style`. Никаких дней недели, ролей, дат окна, чисел. Схемы нет.

Это главный факт инвентаризации: **машиночитаемого слоя не существует**, есть проза
в JSON-обёртке.

### Что реально нашлось по группе 12

Память есть у всех двенадцати (от 3 до 20 активных записей). Про расписание и
доступность — от 0 до 2 записей на человека. Годного к употреблению мало, но оно есть:

- Богачев — «Предпочитает длительные тренировки проводить на субботу»
  (ровно тот случай, вокруг которого крутится п.1 наряда; сборщик и так ставит ему Сб)
- Столова — «Интервалы не ставить на вторник и пятницу» (готовое правило «роль ↛ день»)
- Хофман — «Предпочитает бегать утром» (про время суток, к форме недели отношения нет)
- Лобус — «Единственное доступное время для бега — до 7:00 утра» (то же самое)
- Панина — «На этой неделе вторник пропустила, сложная неделя на работе»
  (одноразовый факт, не постоянное пожелание, но лежит в том же типе)
- Столова — «Может бегать в дни 4, 5, 6, 8 (длительная), 9 недели»
  (**извлечение сломано**: «дни 4,5,6» — это, скорее всего, дни плана, а не дни недели)

### Отсюда три вывода

1. **Годные пожелания и мусор лежат в одном типе.** «Интервалы не ставить на вторник»
   и «вторник пропустила из-за работы» — обе `schedule_constraint`. Отличить их
   автоматически нечем.
2. **Есть прямо ошибочные извлечения** (случай Столовой с «днями 4,5,6»). Если такое
   уедет в планировщик, неделя сломается, и никто не поймёт почему.
3. **Много записей про время суток.** К форме недели они не относятся вообще:
   планировщик распределяет дни, а не часы.

и обратная связь, не планирование.

## Что из этого следует для контракта

Память годится как **источник ПОДСКАЗОК тренеру**, а не как вход планировщика.
Правильный порядок:

1. Пожелание живёт в **отдельной таблице с машиночитаемыми полями**
   (`athlete_week_preferences`): вид, день, роль, окно дат, кто завёл.
2. Заполняет её **тренер** — руками или подтверждением подсказки, вытащенной из памяти.
3. Память остаётся тем, чем является: сырьём с доверием 0.7–1.0 и известной долей
   ошибок извлечения.

Так пожелание становится решением тренера с датой и авторством, а не догадкой модели,
которую никто не проверял.
