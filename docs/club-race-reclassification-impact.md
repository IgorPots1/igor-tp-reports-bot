# Влияние заливки прошлых гонок на классификацию (перед backfill)

Дата: 2026-07-29. Только чтение/код-разведка + read-only счётный скрипт. В БД/TP/Telegram ничего не писал.

Кому: сессии, которая делает enqueue прошлого окна + заливку `trainingpeaks_race_events`.
Зачем: оценка нужна НА ВХОДЕ (до заливки), а не после. Ниже — что именно переклассифицируется,
жёсткий потолок эффекта и как получить точные числа на ваших данных.

## Короткий ответ

Заливка сотен прошлых race-дат **НЕ** приводит к сотням переклассификаций рекордов. Есть две
разные по масштабу поверхности:

1. **Рекорды (мало, ограничено потолком).** Клубный рекорд помечается `race`, только если его дата
   ТОЧНО совпала с race-датой ученика. Рекордов у ученика мало (по одному «best» на дистанцию), и
   флипнется лишь тот, чей PR стоит ровно на дне гонки. **Жёсткий потолок = число различных
   `(ученик, дата)` среди текущих `training_split`-best.** Сколько бы дат ни добавили — больше этого
   не флипнется.

2. **Фидбэк/сравнение (масштабируется с числом дат).** Тренировка на race-дату (в окне последних
   400 дней) исключается из базы сравнения и личных норм, чтобы старт не раздувал «норму». Тут
   «коснётся» ~по одной тренировке на каждую новую прошлую дату в окне — это ожидаемый и полезный
   эффект, не поломка.

## Где это в коде (факт)

- Классификатор: `src/features/club/service.ts` → `classifyRecordType()` (стр. ~3227):
  `raceDatesByStudent.get(studentId)?.has(dateIso) ? "race" : "training_split"`.
- Множество race-дат: `loadRaceDatesWithSource()` (стр. ~3119) — объединение
  `trainingpeaks_race_events` (event_date) + `club_calendar_entries` kind='race'. То есть залитые
  вами race_events прямо туда и попадут.
- Материализация: `materializeClubRecords()` (стр. ~3442) при каждом прогоне вызывает
  `splitByType(evaluated, studentId, raceDates)` — это **re-split**, а не переярлык: кандидат, чья
  дата стала race, уходит из пула training в пул race; training-best дистанции пересчитывается на
  следующий не-race сплит (или исчезает, если другого нет).
- Снапшоты: таблица `club_record_snapshots` (миграция 20260727000000), `student_id uuid` =
  `trainingpeaks_students.id` — тот же идентификатор, что и `trainingpeaks_race_events.student_id`
  (persist пишет `student_id: match.student.id`). Джойн валиден.
- Фидбэк-исключение: `src/features/trainingpeaks/feedback/feedback-enqueue.ts` → `fetchRaceKeys()`
  (стр. ~104), окно `today − 400 дней`. Ключ `${student_id}|${event_date}` из `race_events`.

## Порядок при заливке (важно)

1. **Рекорды не «поедут» сами по факту заливки.** Снапшоты пересчитываются только при следующем
   прогоне `materializeClubRecords()`. То есть план: залили race_events → прогнали материализацию
   (можно с `dryRun` сначала — вернёт rowsWritten без записи) → рекорды отражают новые даты.
2. **Фидбэк-эффект — целевой.** Прошлые старты в окне 400 дн уйдут из базы норм. Тренировки вне
   окна не затрагиваются вообще.
3. **Дистанция гонки в переклассификации НЕ участвует** — только дата. Так что известная
   ненадёжность `race_events.distance_km` (ультра/бэкъярды, нули) на классификацию рекордов не влияет
   (там дистанция берётся из самой тренировки).

## Как получить точные числа на ваших данных

Скрипт read-only, ничего не пишет. Запуск из корня репозитория:

```bash
node --experimental-strip-types --loader ./scripts/_alias-loader.mjs \
  --env-file=.env.local scripts/audit-club-race-reclassification.ts \
  [--scan=tools/trainingpeaks-export/reports/races-scan/<ts>/races.json]
```

Для оценки на ПОЛНОМ ростере сначала сделайте полный **report-only** скан (он пишет races.json и в БД
не лезет — это установленный факт про `tp-scan-events`), затем укажите его `--scan`:

```bash
cd tools/trainingpeaks-export
npm run tp-scan-events -- --from=<прошлое YYYY-MM-DD> --to=<сегодня> --limit=10000
# затем из корня репо — скрипт выше с --scan на свежий races.json
```

Без `--scan` скрипт даёт базу + жёсткий потолок (этого уже достаточно, чтобы понять верхнюю границу).

## Как читать вывод

- `hard_ceiling.max_record_flips_ever` — абсолютный максимум флипов рекордов. Ключевое число.
- `surface_1_records.concrete_flips` — сколько флипнется на конкретном скан-файле сейчас;
  `coverage_gain_new_race_slots` — сколько дистанций-слотов получат race-рекорд, которого не было.
- `surface_2_feedback.concrete_exclusions` — сколько тренировок уйдёт из базы норм (окно 400 дн).
- `projection_by_new_date_count` — экстраполяция флипов/исключений на 100/250/500/1000 новых дат по
  наблюдённым долям; флипы капнуты потолком.
- `notes` — предупреждения чтения (отсутствующая/пустая таблица и т.п.).

Числа я здесь НЕ привожу: из песочницы БД недоступна (креды у Игоря). Скрипт посчитает на реальных
данных при запуске.
