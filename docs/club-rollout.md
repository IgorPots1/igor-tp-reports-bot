# Club rollout — чеклист включения (Фаза 2)

Актуализировано под реальное состояние из `docs/state-of-the-club.md` (Фаза 0) + новое из
Фаз 1 (материализация) и 1.5 (race_events). Прод-проект `wlbswdnpqrcdaqwlfnoo`.

**Принцип.** Всё новое — за флагами ВЫКЛ. Включаем поэтапно, после каждого шага проверяем,
откат = выключить флаг. Прод-миграции применяет Игорь (не агент). Ученикам ничего не уходит
автоматически.

---

## 0. Предусловия (факт из Фазы 0)

- Клубные таблицы УЖЕ существуют в проде (применены raw SQL вне migration-механизма).
  `service_role` имеет полный DML — «грант-блокер» в проде фактически снят. RLS ON, 0 policies
  (deny-by-default для anon/authenticated; приложение ходит через service_role).
- В migration_history клубных миграций НЕТ — файлы в репо это **file-of-record**, БД их опережает.
- Единственная НОВАЯ таблица этого наряда — `club_record_snapshots` (Фаза 1). Её надо применить.

## 1. Миграции — порядок (гранты первыми принципиально; но в проде уже есть)

Применять из папки с main (проверить `git worktree list`). Миграции — файлы, применяет Игорь.

1. **`20260727000000_club_record_snapshots.sql`** (Фаза 1) — НОВОЕ, применить. Создаёт таблицу
   снимков + индексы + грант `service_role` + RLS. Без неё материализация упадёт (42P01), а
   вкладка «Результаты» покажет пусто.
2. File-of-record (описывают уже-применённое, применять только при воспроизведении с нуля,
   ИМЕННО в этом порядке — гранты создаются вместе с таблицами, RLS после):
   таблицы → `*_grants` (service_role DML) → `*_rls`. Список — `supabase/migrations/*club*`.

После применения: открыть `/admin/club/manage` → блок «Доступ к клубным таблицам» должен быть
зелёным (все ОК). Красный 42501 = не хватает грантов; 42P01 = таблицы нет.

## 2. Первичная материализация (один раз, до включения вкладки)

```
cd ~/igor-tp-reports-bot
npm run materialize-club-records -- --all      # полный пересчёт всего клуба (~70с)
```
Проверка: `select count(*) from club_record_snapshots;` → ~262 строки. Вкладка «Результаты»
читает именно их (62с → 0.44с).

## 3. Флаги — порядок включения

| Шаг | Флаг(и) | Что включает | Проверка после |
|---|---|---|---|
| 3.1 | `CLUB_MATERIALIZE_ENABLED=true` | пересчёт снимков в скан-хуках | следующий скан не падает; `computed_at` в снимках свежеет |
| 3.2 | `CLUB_ADMIN_ENABLED=true` | админ-раздел «Клуб» (тренер) | `/admin/club/manage` зелёный; `/admin/club/results` показывает гонки (🏁) и происхождение (tooltip) |
| 3.3 | `MINIAPP_ENABLED=true` + `CLUB_ENABLED=true` | клубный мини-апп | смоук: `npm run smoke-club` → SMOKE PASSED |
| 3.4 | доп. флаги по мере надобности | RACES/WISHES/DAYOFF/PREDICTION/REACTIONS/PRIVACY/BILLING | по фиче — см. таблицу готовности |

Порядок «2-3 ученика → весь клуб»: мини-апп гейтится `resolveClubStudent` (привязка Telegram).
Сначала привязать 2-3 тестовых ученика (в `/admin/club/links`), дать им ссылку, проверить их
кабинет вживую. Убедившись — раскрыть привязку на весь клуб. Флаг `CLUB_ENABLED` общий, поэтому
ограничение «на 2-3» делается через КРУГ привязанных Telegram-аккаунтов, не через флаг.

## 4. Что проверять после каждого шага

- 3.1: скан отработал, в логе нет `[materialize] FAILED`; `select max(computed_at) from club_record_snapshots` свежий.
- 3.2: manage зелёный; ревизия результатов показывает 24 гонки (Фаза 1.5) с происхождением.
- 3.3: `npm run smoke-club` = PASSED (records/feed/challenge/statistics/tops/profile/prediction).
- 3.4: соответствующая вкладка мини-аппа не пустая и не сыпет ошибками.

## 5. Откат

Любой шаг: снять флаг в `=false` (мгновенно, без деплоя схемы). Данные снимков остаются —
безопасно. `club_record_snapshots` можно очистить (`truncate`) без потери авторских данных
(coach_confirmed живёт в `club_records`, не трогается). Миграции откатывать не нужно —
таблицы аддитивны, ничего существующего не ломают.
