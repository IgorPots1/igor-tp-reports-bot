# Открытые вопросы и выбранные дефолты — Mini App «Клуб»

Формат: вопрос / выбранный дефолт / что поменяется, если ответ другой. Работаю автономно на дефолтах, здесь — точки для последующей ревизии Игорем.

---

### 1. Стилистика: «как /m/desk» vs «тёмная/жёлтая/Oswald»
- **Вопрос.** Наряд одновременно требует «стилистика как /m/desk» и «тёмная тема, жёлтый акцент, Oswald + Montserrat». Реальный `/m/desk` — светло-бирюзовый (`#1D9E75`), только Montserrat, без Oswald. Это противоречие.
- **Дефолт.** Технические конвенции беру от `/m/desk` (inline-стили, Telegram init, tab-bar, initData). Палитру — по явным токенам наряда: тёмная тема + жёлтый акцент + Oswald (заголовки) + Montserrat (текст). Клуб получает свою «клубную» айдентику, `/m/desk` не трогаю.
- **Если иначе.** Если нужно 1:1 как desk (светло-бирюзовый, только Montserrat) — меняется только объект токенов `C` в `src/app/m/club/page.tsx` и убирается локальный Oswald-layout. UI-логика не меняется.

### 2. Аудитория мини-аппа
- **Вопрос.** Клуб для тренера (админ) или для учеников?
- **Дефолт.** Ученическая поверхность: ученик видит клубную ленту/топы и свой личный кабинет. Резолвер — `resolveMiniAppStudent`. Изолировано от `/m/desk` (тренер) и `/m/n` (питание).
- **Если иначе.** Если это тренерский обзор — поменять резолвер на `resolveMiniAppCoach` и снять фильтр приватности/сервисных аккаунтов (тренер видит всех).

### 3. Отображаемое имя в ленте
- **Вопрос.** Как показывать имя ученика другим.
- **Дефолт.** Первое слово `student_name` (имя без фамилии) + монограмма (аватара в схеме нет).
- **Если иначе.** Полное имя / ник — поменять `toDisplayName()` в сервисе. Ник потребует новой колонки.

### 4. Цель клубного челленджа (км)
- **Вопрос.** Откуда берётся целевой километраж клуба. В Coach OS нет таблицы челленджей/целей.
- **Дефолт.** Цель — конфиг-константа/фикстура (`src/features/club/constants.ts` + `fixtures/`), помечена как фикстура (`goalIsFixture: true`), в проде цифры не выдумываю — показываю с пометкой «демо-цель». Прогресс (клубный км) — реальный.
- **Если иначе.** Реальная цель → нужна мини-таблица `club_challenges` (goal_km, period) или env-переменная. Дам миграцию-файл при подтверждении.

### 5. Часовой пояс недельного окна
- **Вопрос.** По какому TZ считать «неделю» для км/красавчиков/серии.
- **Дефолт.** Europe/Belgrade (в проекте есть `BELGRADE_TIMEZONE`), ISO-неделя (пн–вс). Гонка недели Run Club была Europe/Moscow — но это другой проект.
- **Если иначе.** Другой TZ/старт недели — одна константа в `constants.ts`.

### 6. Порог «надёжности» рекорда
- **Вопрос.** Когда рекорд «надёжный», а когда «предварительный».
- **Дефолт.** Полоса дистанции ±0.5 км (по наряду). «Надёжный», если есть laps с темпом и CV темпа ≤ 0.08, ИЛИ дистанция в узкой полосе ±0.15 км. 5k всегда «предварительно» (по наряду). Иначе — «предварительно».
- **Если иначе.** Другой порог CV/полосы — константы в `constants.ts`. Если laps почти нигде не заполнены — рекорды массово «предварительные», честно помечаем (цифры не подделываем).

### 7. Ручное обновление данных из мини-аппа
- **Вопрос.** Нужна ли кнопка «обновить сейчас» (тянуть свежее из TP).
- **Дефолт.** Нет. Клуб read-only, едет на существующем ежечасном скане (`workout-cache-scan` + `fit-ingest-scan`). Показываю только индикатор свежести (`getTrainingPeaksWorkoutCacheFreshness`). Ручной скан — attended-операция тренера, вне ученической поверхности.
- **Если иначе.** Если нужен ручной триггер — это отдельный тренерский роут с гейтом, не из `/m/club`; спроектирую отдельно.

### 9. E-Predictor для валидации рекордов — ЗАКРЫТО (реальная модель)
- Исправлено (Блок 5): self-outlier проверка использует РЕАЛЬНУЮ модель Дэниелса `src/app/tools/plan/vdot.ts` (`vdotFromRace`), импортом — локальный дубликат в `records.ts` удалён. Единый источник.
- Логика: реконструированный VDOT кандидата сравнивается с медианным VDOT атлета по ДРУГИМ дистанциям (его уровень по E-Predictor); отрыв > 8 пунктов VDOT → `hidden` (`self_outlier`). Это и есть сверка «против собственного уровня» через настоящую модель, а не суррогат.
- **Возможное усиление (не сделано):** per-athlete якорь из `tp_zone_snapshots.threshold` → предсказанные времена по дистанциям, сравнение с ними напрямую. Оставлено на будущее — self-consistency уже ловит выбросы.

### 10. Порог пауз (pause_gap) — агрессивность
- **Вопрос.** `elapsed/moving > 1.10 → hidden`. На реальных данных это дало 19 отбраковок из 23 — самая частая причина.
- **Дефолт.** 10% (`CLUB_RECORD_PAUSE_TOLERANCE`). Многие тренировки с остановками (светофоры, паузы) исключаются из рекордов как «не непрерывное усилие» — консервативно, по духу наряда «не уверен — не показывай».
- **Если иначе.** Если слишком строго (теряются валидные городские забеги) — поднять до 0.15–0.20. Одна константа.

### 11. records-validation.md содержит реальные имена/результаты учеников

- **Дефолт.** Сохранён как требует наряд (ключевой артефакт). Репозиторий приватный, уже содержит данные учеников.
- **Если иначе.** Если не хочешь это в истории git — добавь `docs/records-validation.md` в `.gitignore` или запускай скрипт локально без коммита вывода.

### 14. Рекорды из лучшего непрерывного отрезка (best-split) — ВКЛ по умолчанию
- Флаг `CLUB_RECORDS_BEST_SPLIT` (дефолт ВКЛ; `=false` возвращает старый метод «вся тренировка»).
- Причина: запись забега длиннее целевой дистанции → время всей записи занижало результат. Скользящее окно по последовательным лапам находит лучший непрерывный отрезок ≈ целевой дистанции. На реальных данных средняя дельта **−146с**, найдено **124** рекорда, которых старый метод не видел (`docs/records-best-split.md`).
- Паузы проверяются ВНУТРИ отрезка (порог 10% не менялся). Нет лапов → падаем на старый метод, метод помечен в модели (`calcMethod`).
- Блок 4: кандидат обязан быть непрерывным беговым усилием — `derived_metrics.workout_type != 'run'` → hidden `not_running`; верхний потолок темпа `720 с/км` (12:00/км) как страховка от прогулок («5k за 2:16» отсекается). Нет валидных кандидатов по дистанции → «нет данных», а не худший.
- **Осталось:** счётчик pause_gap слегка флаки между прогонами (иногда чанк `derived_metrics` не догружается по сети → часть прогулок падает в pause_gap вместо not_running). На показываемые рекорды не влияет; при желании — сделать загрузку derived строже.

### 15. Корневая причина «рекорды медленнее реальных» — ДАННЫЕ, не алгоритм
- Проверено на реале (`docs/records-root-cause.md`): рекордов 86, тип **race 0** (в кэше нет тренировок на даты объявленных стартов — club_races пуст), **44/86 имеют темп в пределах 5% от обычного недельного** — это лёгкие пробежки. «10 км ≈ 60 мин» — НЕ константа (точных дублей нет), просто похожие лёгкие бега. Вердикт: **проблема в отсутствии данных о забегах**, алгоритм выбирает лучшее из имеющегося.
- Следствие: разделил рекорды на `race | training_split` (A#2). В клубные топы идут ТОЛЬКО race → сейчас топы пусты (это честно). На личной карточке — обе категории раздельно («🏁 Гонка» / «🏃 Лучший отрезок тренировки»). Прогноз E-Predictor якорится только на race → сейчас «нет результатов гонок». Флаг не нужен, поведение по умолчанию.

### 16. Доля отбраковок по паузам (A#1)
- Доля, не абсолют: старый метод **19/95 = 20%**, новый (best-split) **~26%** (154/592; число флаки от сетевого недогруза derived). Не упала — потому что best-split строит кандидатов из любой пробежки, а лёгкие бега содержат лап со стопом; проверка elapsed/moving идёт ВНУТРИ отрезка (подтверждено в коде), но лап неделим, поэтому стоп в середине лапа флагует отрезок. Это тренировки, не гонки — согласуется с §15.

### 17. TP Peak Performances (B#2) — доступны per-workout
- Прощупано read-only (`docs/tp-peaks-probe.md`): `getWorkoutDetailsRecord` содержит `meanMaxSpeedsByDistance` (пиковый темп по дистанциям, MM5Kilometer/MM10Kilometer/…, значения м/с). Тренеру видно по подопечным. Отдельного history-эндпоинта по прощупанным путям нет (404). Премиум — у части учеников может быть пусто.
- Это точнее лап-эвристики (без pause-шума), но НЕ решает §15 (пик внутри лёгкой тренировки — всё равно не гонка). **Реализацию не делал** (разведка). Единственные источники истины по гонкам остаются: синк реального забега + `coach_confirmed` + протоколы probeg.org (B#3).

- **Дефолт.** Нет (по наряду) — только место в UI (задизейблено). Ничего не пишется, ничего не уходит ученикам.
- **Если иначе.** Включение реакций потребует таблицы `club_reactions` (миграция-файл) и роута — по отдельному наряду.

## Финальный клубный наряд — решения (2026-07-26/27)

### 18. Материализация рекордов (Фаза 1.1) — ОТДЕЛЬНАЯ таблица
- **Решение.** `club_record_snapshots` — новая таблица под материализованную реконструкцию;
  `club_records` оставлена ЧИСТО под ручные оверрайды тренера (`source='coach_confirmed'`).
- **Почему.** Пересчёт = scoped DELETE+INSERT по затронутым ученикам. Смешать с coach_confirmed
  в одной таблице → пересчёт может снести авторские строки тренера. Разделение делает
  пересчёт безопасным, таблицу оверрайдов — неприкосновенной. Читалка мёржит: coach > snapshot.
- **Замер.** 62 с → 0.44 с на открытие вкладки (~140×); тяжёлая работа ушла на «раз на скан».

### 19. Инкрементальный пересчёт — по «затронутым» через updated_at
- **Решение.** `loadStudentsTouchedSince(sinceIso)` = distinct student_id из workout_cache И
  workout_laps с `updated_at > since`. Ловит и summary (cache), и FIT-лапы (laps) — важно, т.к.
  FIT приезжает позже и двигает только laps. Хук в скан-скриптах за флагом
  `CLUB_MATERIALIZE_ENABLED` (ВЫКЛ), `--since-hours=6`.
- **Компромисс.** Если upsert бьёт updated_at даже на неизменённых данных, окно 6ч может
  пересчитывать шире нужного. Точная передача touched-id из скана — рефинемент на будущее
  (функция уже принимает `--students`). Пользовательский выигрыш (быстрая вкладка) достигнут
  при любом варианте; это лишь про CPU Mac-раннера. Первичная популяция — разовый `--all` в rollout.

### 20. Пороги (Фаза 1.3) — VDOT «потолок 65» в коде НЕ существует
- **Факт против наряда.** Жёсткого VDOT-cap нет. Есть относительный `SELF_OUTLIER_VDOT_MARGIN=8`
  (implied VDOT выше СОБСТВЕННОГО VDOT ученика на др. дистанциях +8 → hidden). На полных данных
  срабатывает 11 раз из 11910 — сильных не режет. Верю факту, не наряду.
- **Что реально режет.** `pause_gap` (порог пауз 10%) — 1303 = 74% всех отбраковок. Единственный
  порог, требующий внимания. 5%-й lap-mismatch — 21 (спокоен). Пороги НЕ менял (по наряду —
  отдельным нарядом). Детали — `docs/records-full-data.md`.

### 21. BLOCK 3 (Фаза 1.4) — конверсия ~17 диагностических скриптов ОТЛОЖЕНА
- **Решение.** Не делаю слепой свип в этом наряде. Причины: (1) скрипты ортогональны клубу
  (coach-memory / operational диагностика, не club); (2) read-only, не в боевом пути вкладок;
  (3) часть `.limit(N>1000)` НАМЕРЕННАЯ — `scripts/measure-feedback-pagination.ts` специально
  держит `.limit(6000)/.limit(40000)`, чтобы показать СТАРОЕ усечённое поведение против нового.
  Слепая замена сломала бы замер. Каждый скрипт требует индивидуального суждения.
- **Оставлено.** Список 17 файлов — в `git grep '.limit(' scripts tools` (>1000). Конверсия
  по-скриптно — отдельный механический наряд. Eslint-правило уже защищает `src/**` (боевой код).

### 22. race_events как источник гонок (Фаза 1.5)
- **Решение.** `trainingpeaks_race_events` (133 реальные гонки, 60 учеников) подключён как
  источник race. Механизм: `loadRaceDatesWithSource()` мёржит race_events (приоритет) +
  club_races; `loadRaceDatesByStudent` строится из него (union) → `classifyRecordType` теперь
  видит даты гонок → тренировка того дня типизируется как race. Время берётся из тренировки.
- **distance_km НЕ используется.** По коду repository.ts:2449 он ненадёжен (ультры мис-парсятся).
  Дистанция рекорда-гонки — из сматченной тренировки (реконструкция), не из race_events.
- **Дедуп.** Дата в обоих источниках → один источник по приоритету (race_events > club_races) →
  одна race-запись. Задвоения нет по построению (reconstruct берёт лучшее на дистанцию).
- **Провенанс (1.5.3).** snapshot.source и RevisionRecord.source несут race_events/club_races;
  видно в админ-ревизии (tooltip на ячейке) и в снимке.

### 23. E-Predictor якорь (1.5.4) — уже выигрывает, target остаётся из club_races
- **Якорь.** `getClubPrediction` → `studentRecordsFromRows` → `loadRaceDatesByStudent` (теперь с
  race_events) → база `records.filter(recordType==='race')` наполняется автоматически. Кода менять
  не потребовалось — рефактор дат протёк насквозь.
- **Target (предстоящая гонка).** Оставлен на club_races: там есть надёжная `distance_meters`.
  У race_events distance_km ненадёжен — брать целевую дистанцию оттуда рискованно (ультры).
  Возможность (не делаю): научить target брать будущий race_events, если удастся надёжно
  распарсить дистанцию из distance_raw/title. Зафиксировано как отдельная возможность.

### 24. race_events в предстартовых слоях (1.5.4) — УЖЕ подключено
- Проверено фактически: `comparison/resolve-window.ts` использует будущий старт из race_events
  для окна сравнения; `nutrition/repository.ts` (2250/2288/2311) — предстартовое питание/taper;

  race_events (title, event_date) — сверка протоколов остаётся отдельным нарядом.

### 25. Исполнение стартов в TP (Фаза 3) — переиспользуем create_workout
- **Решение.** Одобренный старт (club_races) → спек `create_workout` (планируемый забег в
  календаре TP): athleteId, workoutDay=race_date, title=name, workoutTypeValueId=**3 (run,
  подтверждён)**, distancePlanned=distance_meters. НЕ изобретаем «race» type-id. Модуль
  tp-execution.ts ЧИСТЫЙ (без enqueue/сети). Реальный путь — createTrainingPeaksAction →
  существующий пайплайн (dry-run→подтверждение→раннер→verify→откат create→delete).
- **totalTimePlanned не проставляем.** Единица этого поля на write-payload не подтверждена —
  целевое время из target_result_seconds помечено unresolved, а не отправлено в неверной единице.
- **Флаг** CLUB_TP_EXECUTION_ENABLED (ВЫКЛ). Реальное исполнение НЕ запускалось. Dry-run —
  docs/club-tp-dryrun.md (0 накопленных заявок сейчас + синтетический пример payload).

### 26. Исполнение выходных (Фаза 3) — РУЧНОЙ review-case, не авто-действие
- **Решение.** Выходной НЕ имеет проверенного TP-представления: нет подтверждённого type-id
  «отдых/выходной», а деструктивная трактовка («снять запланированные сессии на from..to»)
  опасна и НЕ фабрикуется. planClubDayoffAction возвращает review-case (тренер применяет в TP
