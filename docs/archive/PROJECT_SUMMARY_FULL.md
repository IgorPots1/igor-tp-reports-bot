## 1. Что за проект

### Назначение
Coach OS — операционная система тренера Игоря (бег). Nutrition-блок берёт недельный отчёт ученика по питанию (PDF/CSV/TXT из FatSecret), сопоставляет его с тренировками из TrainingPeaks и генерирует:
1. **Разбор за прошлую неделю** (по дням + итог) — в голосе Игоря, готовый к отправке в Telegram.
2. **План на следующую неделю** (мини-таблица по дням с целями ккал/Б/Ж/У под тип тренировки).

Поток всегда **attended**: draft → approve тренером → отправка вручную. Никаких авто-отправок ученику.

### Архитектура (числа кодом, проза моделью)
Жёсткое разделение ответственности — это центральное архитектурное решение всего проекта:

| Держит КОД (детерминированно) | Держит МОДЕЛЬ (проза) |
|---|---|
| Все числа: фактические макросы, цели (`target`), недобор | Проза комментария по дню (`day_prose`) |
| Факт-строка «ккал · Б · Ж · У (г/кг)» | `coach_summary_text` (тренеру) |
| Классификация дня (`normalizeTrainingType`) | `day_by_day_analysis_text` |
| EA, energy floors, macro guardrails, выбор фокуса, safety | `athlete_message_draft` |
| Структура сообщения, приветствие, мини-таблица, pre-training | называние конкретной еды (в рамках fat-policy) |
| Политика жиров (что можно озвучивать) | — |
| Валидация прозы (числа/статус) | — |

Финальное сообщение ученику собирает **детерминированный рендерер** (`renderNutritionTelegramMessage`) из canonical `daily_analysis`, а не сырой вывод LLM. Модель только «раскрашивает» уже посчитанные коду факты словами.

### Сквозной пайплайн
```
[PDF/CSV/TXT отчёт]
  → file-intake.ts        ккал/Б/Ж/У по дням; ДАТЫ из PDF = источник истины (не из UI-недели)
  → context.ts            + TP-кэш (прошлая completed_only / следующая all), профиль, цель,
                            вес, заметки, safety-флаги
  → methodology.ts        EA, energy floors, macro guardrails, canonical daily targets,
                            сигналы, выбор ОДНОГО фокуса недели
  → draft-generator.ts    review: AI-путь (Anthropic/OpenAI) или fallback-шаблон
                            → upsert в nutrition_weekly_analyses
  → weekly-plan-formulas.ts  план на следующую неделю по табличным формулам от веса
  → combined-message.ts   DERIVED-текст из canonical daily_analysis (primary copy path)
  → telegram-renderer.ts  финальное сообщение ученику + валидация
```

### Стек
- **Next.js** (App Router, server actions) + **Supabase** (Postgres, RLS, service_role) + **TrainingPeaks** (кэш тренировок).
- **LLM-провайдер**: адаптер (`nutrition-ai-provider.ts`) — Anthropic по умолчанию (`claude-sonnet-4-6`, через raw fetch), OpenAI как fallback.
- **Хранилище разбора**: таблица `nutrition_weekly_analyses` (jsonb `nutrition_summary`).
- Деплой: Vercel preview по ветке; прод-push/деплой делает только Игорь. Миграции — файл в `supabase/migrations/`, применяет Игорь вручную перед деплоем.

## 3. Методики (содержательно)

### 3.1 Снижение веса (lose) — `weekly-plan-formulas.ts`

**Якорь maintenance (исправленный, Task 10b).** Раньше дефицит считался от раздутого фиксированного коэффициента (rest 35 ккал/кг → ~2450 для 70 кг). Теперь:
```
maintenance_day = RMR × NON_EXERCISE_PAL(1.3) + TP-расход_этого_дня
```
- **RMR** (`estimateRestingMetabolicRate`, `:580`):
  - **Mifflin–St Jeor** если есть рост+возраст (точно): `10·вес + 6.25·рост − 5·возраст` (+5 муж / −161 жен), пол неизв. → как жен.; не ниже 800.
  - **Cunningham/FFM** (приближение, если нет роста/возраста): `500 + 22·FFM`, FFM = вес × {жен 0.78 / муж 0.82 / неизв 0.8}.
  - Поэтому для худеющих рост/возраст заполняем — иначе тренировочные дни уходят выше (Cunningham-приближение).

**Периодизированный дефицит** (`LOSE_DEFICIT_BY_DAY_TYPE`, `:539`) — «топливо под работу», больше режем в покое, минимум в тяжёлые дни:
```
rest 500 · easy 400 · cross 350 · strength 300 · pre_long 250 · hard 200 · race 200 · long_run/long_endurance 150 · unknown 350
```
Недельное среднее → умеренный коридор 300–500 ккал/день.

**EA-пол (safety-clamp, дефицит не может его пробить):**
```
eaFloor = FFM × 30 + exercise_kcal
kcal_day = max(maintenance − deficit, max(eaFloor, absFloor)), округление до 50
```
- Белок высокий (≈1.9 г/кг — держать массу в дефиците), жир 20–30% энергии, углеводы заполняют остаток.
- **gain**: профицит `maintenance × 1.11`, белок 1.8 г/кг.
- **maintain**: путь не тронут (байт-в-байт), идёт по фиксированным коэффициентам.

**Проверено на Любови Селезневой (70 кг, жен):** lose Mifflin → rest 1800 / easy 2100 / hard 2250 / long 2600 (длительная ≈ поддержание, НЕ 3000). Safety не ослаблен целью: 900 ккал/день + lose → всё равно `blocked_safety`.

### 3.2 Старты / загрузка — `computeNutritionRaceProtocol` (`weekly-plan-formulas.ts:224`)

Протокол по дистанции (`distanceKm` из TP-события):

| Дистанция | Загрузка | Дней | Гель за ~10 мин | Усилие >90 мин |
|---|---|---|---|---|
| < 10 км (5K) | нет | — | нет | нет |
| ≥ 10 км (10K) | нет (интенсивный день, не загрузка) | — | **да** | нет |
| ≥ 21 км (HM) | 6–8 г/кг | 2 | да | да |
| ≥ 42 км (M) | 7–9 г/кг | 3 | да | да |
| ≥ 50 км (ultra) | 8–10 г/кг | 3 | да | да |

Ключевые правила:
- **Загрузка — только для усилий >90 мин (полумарафон+).** 5K/10K — интенсивные гоночные дни БЕЗ загрузки.
- **Гель — твёрдое правило для ≥10 км** (5K — без геля), за ~10 минут до старта.
- **Тайминг по названию** (времени старта в TP нет): «ночн/вечер/night/evening» → `evening_or_night` (углеводы распределить по дню, последний полноценный приём за 2–3 ч до старта); иначе → `morning` (углеводный ужин накануне).
- **lose + старт → дефицит ВЫКЛЮЧАЕТСЯ в race-week** (`raceWeekDeficitOff`, `:734`): неполный гликоген + здоровье = нельзя выходить на старт на дефиците. Тренировочные дни → к поддержанию; дни отдыха на EA-полу не двигаются. Вне недели — обычный дефицит. Half+ загрузка заложена, на реальном ученике пока не обкатывалась.

Распознавание старта (`isNutritionRaceTitle`, `methodology.ts`): Unicode-boundary (`\p{L}` lookarounds, флаг `u` — ASCII `\b` не ловит кириллицу); исключает ложные «в темпе марафона», «марафонским темпом», «маршрут забега», «подготовка к».

### 3.3 Активности (не-беговой расход) — `activity-energy.ts`

Коэффициенты ккал/кг/час, проверяются ДО беговой/дневной интенсивности. Расход всегда от веса (`длительность × вес × коэф`) — TP не отдаёт измеренные калории в кэш, только TSS, HR-сверки нет. Общий для review и plan-путей, чтобы не расходились:
```
walk/ходьба 3.5 · hike/поход 6 · padel/падел 7 · tennis/теннис 7 · swim/плавание 7 · bike/вело 5 · strength/силовая 5
```
Силовая консервативно (20–50 мин, интенсивность не читаем) — лучше недооценить.

### 3.4 Ядро методики разбора — `methodology.ts`

- **Energy Availability:** `EA = (intake − exercise) / FFM`. Зоны: <30 красная, 30–45 жёлтая, ≥45 зелёная. Confidence `high` только если FFM измерена И энергия из реального TP — на практике почти всегда `medium`.
- **Энергетические полы** (`calculateNutritionEnergyFloorFacts`): отдых 25×вес · нагрузка/силовая/кросс 30×вес · тяжёлая/длительная/гонка 35×вес.
- **Макро-гардрейлы:** белок <1.1 мало / 1.5–2.0 ок / >2.0 высоко; жир <0.8 низко / >1.6 или ≥40% энергии высоко (coach-only по умолчанию); углеводы — band под тип дня (ориентир, не предписание).
- **Canonical carb target по типу дня:** отдых 3–4.5 · лёгкая 3.5–5 · тяжёлая/гонка 5–6.5 · pre-long 5.5–6 · длительная 6–7 · длинная выносл. 6–8 · силовая 4–6 · кросс 5–7 г/кг.
- **Формулы плана** (`DAY_TYPE_TARGETS`): отдых 35 ккал/кг / лёгкая 39 / тяжёлая 43 / длительная 45 / силовая 39 / кросс 39; округление ккал до 50, углеводы до 10, белок/жир до 5.
- **Один фокус недели** (`selectNutritionWeeklyFocus`) — ровно один по жёсткому приоритету: blocked_safety → limited_data → severe EA → long_run_underfueling → hard_session_underfueling → post_hard_recovery → carbs_around_key_sessions → weekly_consistency → protein_support → maintenance. К фокусу прикреплена `progressionStrategy` (small_step / moderate_step / toward_reference_band / maintain).

## 4. Архитектурные решения

1. **Sonnet для прозы, код для чисел.** Дефолт `claude-sonnet-4-6` через raw fetch (`nutrition-ai-provider.ts`); OpenAI — fallback. Модель не пересчитывает ничего: kcal/Б/Ж/У/г-кг/targets/day type/status/focus/safety/race — всё из facts JSON.
2. **Hard/soft блокировки (two-tier).** Hard-флаги (`buildNutritionSafetyFlags`, `context.ts:585+`) → полная блокировка текста ученику (`athlete_message_draft=null`, статус `blocked_safety`): РПП/анорексия/булимия; компенсация/наказание едой; мед.состояния (диабет, беременность, послеродовой, аменорея); стресс-перелом; **≥2 дней <1300 ккал**; **≥3 дней <90 г углеводов**; **потеря веса ≥4%**. Soft-флаг (кето/IF + бег) — предупреждение, не блок. После `030fd30` только клиническая опасность hard-блокирует на уровне рендерера.
3. **Тройной гард на числа.** Числа в прозе только из PDF/facts, никогда из слов ученика. `validateNutritionDayProse` (`telegram-renderer.ts`): `number_not_in_facts` — каждое число прозы ∈ allow-set (`buildAllowedNutritionProseNumbers`: actual + округления, target + округления 5/10/25/50); `status_softened` — жёсткий день обязан иметь маркер недобора. Допуск точного совпадения <0.1, шаги округления [5,10].
4. **Слова ученика → тон, не числа (Блок 3).** `report.rawText` → `athlete_comment` в facts: влияет на тон (старание → тёплая похвала; «болела/устала» → мягче; «ела X перед бегом» → отрази), обстоятельства, опенинг-строку. Числа из слов брать ЗАПРЕЩЕНО (дигит-гард на `athlete_opening_note_ru`). Старание/обстоятельства можно озвучить ученику тепло; медицинское — только тренеру.
5. **«Свой режим» (own_regime).** Флаг профиля заменил хардкод фамилии (`applyNutritionFatPolicyOverrides`): не оценивать калорийность/жир как проблему (слой A — тон/feedback, без вмешательства в числа). Слой B (числовой override) отложен.
6. **coach_override safety-блока.** `safety_flags.blocked` остаётся true (честная запись), `coach_override` релизит текст; статус → needs_review (никогда не авто-send); глобальный порог не трогается. Combined/план уважают override через ранние early-return в `isReviewBlockedSafety`/`isPlanBlockedSafety`/`isSafetyBlocked`.
7. **Один вызов LLM на разбор+план** (Task 6) — экономия и согласованность.
8. **Даты из PDF — источник истины** (не из UI-недели).

## 5. Грабли и уроки

1. **Повторяющийся баг: валидатор ложно режет честную прозу.** `status_softened` срезал 4/7 и 3/7 дней на живых данных (Khadizhat 14.06) — проза несла недобор словами, которых не было в списке маркеров. Список маркеров расширяли минимум дважды (`5017060`, `779fd6e`). Урок: русский язык богат, регэксп-список маркеров — хрупкая основа; вариант A (качественная подача без форсированного грамм-числа) снизил риск, но на жёстких днях ещё бывает (открытая задача г).
2. **ASCII-границы не работают с кириллицей.** `\bзабег\b` никогда не матчил «Ночной забег»; `\w*` не ловил «марафонским темпом». Перешли на `(?<![\p{L}])…(?![\p{L}])` + флаг `u`. Урок: для русского — только Unicode-aware регэкспы.
3. **Структурные фиксы, не заплатки.** coach-override сначала «работал» в `athlete_message_draft`, но combined всё равно был `blocked_safety` — потому что у combined были ещё ДВА независимых гейта + гейт в plan-генераторе. Заплатка в одном месте не лечит — нашли все три точки и провели `coach_override` сквозь них. Тот же урок — «баг отдыха» чинили дважды в двух функциях классификации (`normalizeTrainingType` и `normalizeDayType`), потому что логика дублирована (риск рассинхрона, см. аудит).
4. **Fallback маскирует сбои (9 точек тихого отката).** Один 429/400 от провайдера → весь разбор в шаблон, причина не видна без диагностического скрипта. По-дневный срез валидатора (#8) вообще не пишется в `notes` — слепая зона. До `91697ca` все отказы были немыми. Урок: тихий fallback = «выглядит как будто ничего не поменялось», хотя под капотом каждый раз своя поломка.
5. **Обкатка как QA.** Главный механизм качества — прогон на реальных учениках, каждый вскрывает свой пробел (см. раздел 7). Phase 1 (`72c6cf7`) ни разу не отрендерилась на живых данных — все живые прогоны падали раньше (400→пустые поля→ложный срез→429). Урок: зелёные юнит-тесты ≠ работает в проде; верифицировать на живых данных.
6. **Экономия генерации.** Реальный AI-прогон ≤1 на чекпойнт; структурные изменения проверять на уже сгенерированном/детерминированном тексте. Наряды — средние (не микро, не гигант), чекпойнт на каждый.

## 8. Открытые задачи и carry-forward

### Незакрытые тех-задачи (всплыли на обкатке, не начаты)
- **(а) Качество углеводов — по ПРОДУКТУ.** Сейчас модель может звать банан/булочку/лаваш «медленными». Надо: медленные = крупы/рис/картофель/паста/хлеб/бобовые; быстрые = банан/выпечка/сладкое/лаваш/белый хлеб. Малоуглеводное (борщ, салат) — НЕ углеводная основа. Содержание углеводов брать из PDF (item carbs).
- **(б) Две тренировки в день (бег + силовая) — вторая теряется.** `buildWorkoutContextByDate` берёт primary по `WORKOUT_LOAD_PRIORITY`, вторая сессия не учитывается в расходе/типе дня. Надо суммировать нагрузку/расход за день.

- **(г) Grushevskaya среда-интервалы иногда теряет pre-workout заметку.** day_prose жёсткого дня падает в детерминированный фолбэк (строгий валидатор отклоняет диапазоны-недоборы «60–70 г»). Вариант A снизил риск, не убрал. Кандидат: разрешить валидатору недобор-диапазоны или промпт «одиночные округлённые числа».

## 9. Принципы работы

- **Голос Игоря.** Тёплый, поддерживающий, без стыда и без медицинских терминов (RED-S/LEA/энергодоступность/дефицит/диагноз — запрещены ученику). Конкретные дни с числами, практические шаги «добавь порцию риса/каши», «не резко за один день». Допустимо ученику: «энергии для такого дня маловато», «нижняя граница». Few-shot эталоны в `narrative-guardrails.ts`.
- **Цикл draft → approve → checkpoint.** Claude делает работу в отдельной ветке + проверки (`npm run lint`, `npx tsc --noEmit`, относящиеся `check-*`). Игорь пушит ветку (Vercel preview) → смотрит → fast-forward main → один `git push`. Максимум 2 push от Игоря на фичу. Прод-push/деплой/миграции — только Игорь. Никогда не коммитить/пушить/деплоить без явного «да».
- **Экономия генерации.** Реальный AI-прогон ≤1 на чекпойнт; структурное проверять на готовом/детерминированном тексте. Наряды средние, чекпойнт на каждый.
- **Числа.** Факт точно / цель округлённо («около 350») / per-item carbs из PDF. Валидатор полицирует макро в day_prose (тройной гард).
- **maintain байт-в-байт.** Методику/числа/safety/формат не ломать; lose не обходит safety.
- **coach-override safety.** Ручной, per-report, с подтверждением, всегда needs_review, логируется; порог не меняется; авто-разблокировки нет.
