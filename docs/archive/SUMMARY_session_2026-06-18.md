## 1. Качество углеводов по ПРОДУКТУ (Часть А, `6d2a3df` + `c793961`)

**Проблема обкатки:** модель звала банан/булочку/лаваш «медленными углеводами»; качество углевода было целиком на усмотрении модели (промпт), кода-классификации не было.

**Решение** — новый модуль `carb-quality.ts`:
- `classifyCarbItem(name, carbsGrams) → fast | slow | neutral | not_carb_base`.
- Порядок: **грамм-гейт** (`CARB_CONTRIBUTOR_MIN_G = 20`, единый с `carb_contributor`) → `fast` → `slow` → `neutral` (дефолт). Fast проверяется первым (защита: «овсяное печенье» → fast, не slow).
- Unicode-aware (`(?<![\p{L}])` + флаг `u`).
- Тег `carb_class` прокинут в facts (`by_section` + `carb_foods`); единый селектор `selectNotableFoodItems` (один источник, без дублей).
- Промпт: «класс бери из факта `carb_class`, не по наитию».
- **Гард `carb_quality_mismatch`** в `validateNutritionDayProse` — ловит РОВНО fast-продукт, названный «медленным».

**Важная развилка (верификация перед коммитом):** гард на fast **+ neutral** давал **4/9 ложных срезов** на реальной прозе (рис/паста/картофель «медленные» — идиома тренера). → Сузили гард до **fast-only**. Урок #1 (валидатор не должен резать честную прозу) сработал в обе стороны.

`c793961`: пример «добавь порцию» → «крупа или **паста**» (рис убран из ПРИМЕРА, не из классификатора); строка «carb_class=fast — углеводы засчитываются, но НЕ называть „правильным источником“/„углеводной основой“».

Чеки: `check-nutrition-carb-quality`.

## 2. Две тренировки в день — суммирование расхода (Часть Б, `63695cd`)

**Проблема:** день с бег+силовая считал расход только ОДНОЙ сессии (primary по priority), вторая терялась → maintenance/EA занижены. У Нади четверг (бег+силовая) считал силовую-длительность под беговой коэф, бег вообще терялся (360 ккал вместо 705).

**Решение:**
- `activity-energy.ts`: общий хелпер `sumDaySessionsExpenditureKcal` (один на оба пути, урок #3 — не чинить дважды). Длительности НЕ складываются под один коэф: каждая сессия своим методом, потом сумма.
- review (`methodology.ts`): `WorkoutContextByDate.sessions` хранит ВСЕ сессии; `estimateExerciseEnergyKcal` суммирует через `estimateSessionEnergyKcal`. Одиночные дни байт-в-байт.
- plan (`weekly-plan-formulas.ts`): сумма по `dayWorkouts` (primary держит pre_long-тип, вторичные — свой dayType). Одиночные/пустые дни байт-в-байт.
- Тип дня (effectiveType) НЕ тронут. maintain-формулы не тронуты (меняется только вход — расход).

**Верификация (worktree до/после):** четверг Нади 360→705; план lose 1900→2100; дни без 2 сессий — байт-в-байт. Чек `check-nutrition-two-workouts-expenditure`.

## 3. Safety-блок → пометки: ТРИ захода (`ea63ab2` → `b696d66` → `a85ebc4`)

**Почему три коммита — ключевой урок сессии:**
1. **`ea63ab2`:** `buildNutritionSafetyFlags` → `blocked=false`, `doNotSendReasons=[]`. Убрана override-кнопка/проводка. **НО** `hard_flags` оставили заполненным «для записи тренеру».

Свежая генерация снова блокировалась. → `hard_flags=[]`, сигналы в `softFlags` (advisory). Но **СТАРЫЕ строки в БД** уже хранят hard_flags/status/do_not_send → combine читает сохранённое → блок остаётся.
3. **`a85ebc4` (кардинально):** симптом — «сохранённая строка продолжает блокировать» — лечится в **ГЕЙТЕ отображения**, не в источнике. `isReviewBlockedSafety`/`isPlanBlockedSafety` теперь блокируют ТОЛЬКО по genuine non-safety причине модели, игнорируя: легаси-статус `blocked_safety`, `safety.blocked`, все `manual_review_required:*`. → **старые строки разблокируются БЕЗ перегенерации** (гейт работает на рендере). Escape-hatch: модель-эмитированный не-safety do-not-send ещё блокирует.

**Урок:** «структурный фикс, не заплатка» — чинить надо там, где симптом (гейт), а не только источник; и помнить про УЖЕ сохранённые данные.

Промпт-правило `КРИТИЧЕСКИ НИЗКИЕ ДНИ` (always-on при `very_low_kcal_days`): тёплая прямая пометка про опасно низкие дни. Чек `check-nutrition-safety-blocks` (инвариант `hard_flags.length===0`), `check-nutrition-safety-override` удалён.
