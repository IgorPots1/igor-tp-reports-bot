Дата: 2026-07-26. Ветка `feature/sweep-health-index`. Только чтение для разбора; правки — алерт-классификатор, смоук-скрипт, package.json. Проверки: tsc/eslint/build/smoke — 0.

## 1. Постмортем краша (по логам)

### Что за краш
Прод-фикс пагинации заставил `fetchIn` сортировать по `id`; у таблицы
`trainingpeaks_student_health_metric_profiles` колонки `id` НЕТ (ключ `student_id`)
→ чтение профилей в `assemblePlannerInputsForWorkouts` бросает
`column ... .id does not exist`. Починено в `984eb1d` (параметр `orderBy`, профили
по `student_id`) — уже в origin/main.

### Дошёл ли до прода — НЕТ
`trainingpeaks_cron_run_logs`, job `workout_feedback_enqueue`: **40 прогонов, ВСЕ `sent` (успех), 0 `failed`**, диапазон 2026-07-23 19:24 … **2026-07-26 12:10** (последний). Последний прогон был ДО вечерних мержей (прод-фикс + окна) этой сессии, и уже несёт фикс. **Ни один прогон не выполнил багованный код → 0 потерянных прогонов, досоздавать нечего.** Баг был латентным и пойман (parity-harness'ом при наряде окон) до первого исполнения.

### Как именно падал бы — ГРОМКО (не молча)
Раннер `tools/…/tp-feedback-enqueue-run.ts` (и HTTP-роут-бэкап) оборачивают свип в
try/catch: пишут `cron_run_logs` статус **`failed`** + `errorMessage`, `console.error`,
`process.exit(1)`. То есть это НЕ тот же класс, что тихое усечение — отказ виден в
логе прогонов. Проблема была не в «глотании», а в том, что **никто не смотрит** в
`cron_run_logs` (см. п.2).

### Досоздание — не нужно
Свип **репорт-триггерный и идемпотентный**: он ставит в очередь только связку
«отчёт → пробежка без джоба», и на следующем прогоне до-подхватывает пропущенное.
Отдельный бэкфилл-скрипт не нужен: у самого свипа есть dry-run —
`sweepAndEnqueueReportedRunWorkouts({ dryRun: true })` возвращает `details` (что
было бы поставлено). Запускать не нужно (0 пропущено).

### Почему не поймали до мержа
tsc/eslint/next build **не исполняют запрос** к реальной схеме — ошибка «нет
колонки» вылезает только в рантайме. Ни одна из трёх зелёных проверок такое не
ловит. Закрывает пробел смоук п.3 (исполняет боевой путь against БД).

## 2. Алерт на тихий/нулевой/упавший прогон (реализовано, минимально)
Запись статуса прогона УЖЕ есть (`cron_run_logs`: started→sent|failed + counts +
errorMessage). Не хватало **видимости**. Добавлено:
- `src/features/trainingpeaks/feedback/sweep-health.ts` — чистый классификатор
  `classifySweepHealth` + загрузчик `loadFeedbackSweepHealth()`: `ok | info | alert`
  с кодами `no_runs / failed / stuck / stale(>30ч) / zero_output / ok`.
- `scripts/check-feedback-sweep-health.ts` — печатает статус, exit≠0 при `alert`
  (для монитора/чек-листа). Уведомления НЕ шлёт — только видимый статус.
- **UI-ready:** индикатор в админке — одна строка
  `const h = await loadFeedbackSweepHealth(); <badge level={h.level}>{h.message}</badge>`
  (не встроил в конкретную страницу, чтобы не трогать большой `/admin/reports`;
  функция готова к вставке).
Прогон сейчас: `[INFO] последний прогон 12:10 — 0 в очередь` (норма: 29 отчётов, все
уже обработаны/старты; `reportsRunIsRace=2` — исключение стартов работает).

## 3. Смоук боевого пути (реализовано, в чеклист)
`scripts/smoke-feedback-sweep.ts` — берёт ОДНУ свежую пробежку, гоняет
`assemblePlannerInputsForWorkouts + buildFeedbackContextPacket` (тот самый путь с
чтением профилей), **без записи и без отправки**, печатает `PASSED` или
`FAILED at [шаг]: …`, exit≠0 при падении. Прогон: **PASSED**. На багованном коде
упал бы на шаге `[assemble]` — то есть этот смоук поймал бы краш.
Добавлен в `package.json`: `npm run smoke-feedback-sweep`. **В чеклист перед мержем
фидбек-пути — наравне с tsc/eslint/build.**

## 4. Health-индекс — НЕ нужен (уже есть)
Индексы на `trainingpeaks_health_metrics_cache`:
- `(student_id, metric_date DESC)` — **УЖЕ ЕСТЬ** (`…_student_metric_date_idx`)
- `(metric_key, metric_date DESC)`, `(trainingpeaks_athlete_id, metric_date DESC)`, PK, unique.

`EXPLAIN ANALYZE` реального запроса окна (18 учеников, 4 метрики, 60 дней, limit 1000):
**Execution 512 ms**, Index Scan по `…_student_metric_date_idx` (Index Cond:
student_id AND metric_date≥). Быстро. Statement timeout ранее был **транзиентным** —
от моей повторной тяжёлой нагрузки на БД в тестах (5+ полных assemble подряд), а не
от отсутствия индекса. **Миграция не нужна.** (Микро-нюанс: `.order("id")` в
пагинации добавляет сортировку 233kB — незначимо при 512ms; при желании ускорить
можно листать по `(student_id, metric_date)`, но это не требуется.)
