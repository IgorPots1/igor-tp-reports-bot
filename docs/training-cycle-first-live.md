Состояние на 2026-08-12. Документ написан ПЕРЕД заведением; сам цикл не заводился.

## Состояние: читатель есть, миграция ждёт применения

Вставленная в `training_cycles` строка со `status = 'active'` ТЕПЕРЬ ЧИТАЕТСЯ и главнее
черновика по истории. Модуль — `lib/cycle-reader.ts`, функция `loadActiveCycles(sb, weekStart)`.
Проверено тремя проверками в `check:cycle-forecast`, все мутационно подтверждены.

Осталось одно действие Игоря: **применить миграцию `20260920000000_training_cycles_reader_columns.sql`.**
Без неё читатель работает (он сам обходит отсутствие колонок), но с двумя ограничениями:

| колонка | если миграции нет | если применена |
|---|---|---|
| `start_week` | цикл всегда читается как «неделя 1» — роль недели не двигается | позиция считается от начала цикла: рост / разгрузка / подводка идут по плану |
| `days` | число дней берётся из истории | число дней задаёт тренер |

Миграция также вешает уникальный индекс «один активный цикл на атлета» — раньше два
активных цикла на одного человека не были запрещены и давали неопределённое поведение.

### Что читатель делает и чего не делает

- Заведённый цикл — РЕШЕНИЕ ТРЕНЕРА, черновик из истории к нему не подмешивается вообще.
  Единственное исключение — `days = null`, что явно означает «как в истории».
- `base_aerobic_min_manual` главнее `base_aerobic_min`. Ручная база теперь живёт в данных,
  а не списком `MANUAL_BASE` в коде.
- Цикл, у которого неделя вышла за `length_weeks`, просто перестаёт действовать —
  атлет возвращается на прежний путь без ошибки.

## Как завести

Читатель готов. Если миграция ещё не применена — заводить можно, но `start_week` и `days` будут проигнорированы (см. таблицу выше).

```sql
-- ПЕРВЫЙ ЖИВОЙ ЦИКЛ. Числа взять из пакета приёмки на ту же неделю, не выдумывать.
insert into public.training_cycles (
  trainingpeaks_athlete_id, intent, target_date, status,
  length_weeks, base_aerobic_min, base_quality_min,
  start_week, days, notes, created_by
) values (
  5905779, 'half', '2026-09-12', 'active',
  5, 250, 25,
  '2026-08-17', 4, 'первый живой цикл, заведён вручную', 'igor'
);
```

`base_aerobic_min` и `base_quality_min` — это БАЗА, а не цель первой недели: цель считает
`forecast()` шагом ×1.06 от базы. Сверить с пакетом: там у неё цель недели 275 = 250 + 25.

## Как проверить, что включилось

1. `select id, status, base_aerobic_min from training_cycles where status = 'active';` —
   строка одна, статус `active`.
2. Прогнать `npx tsx tools/trainingpeaks-export/scripts/tp-cycle-week-acceptance.ts` и
   посмотреть в шапке «АКТИВНЫХ ЦИКЛОВ В БАЗЕ СЕЙЧАС: 1» вместо 0.
3. В её шапке строка должна начинаться со слов **«ЦИКЛ ТРЕНЕРА (из training_cycles)»**,
   а не «ЧЕРНОВИК из истории», и в ней — прочитанные числа. **Проверять именно это:**
   поставить в таблице базу, заведомо отличную от расчётной (например 300 вместо 250),
   и убедиться, что цель недели поехала.
4. `npm run check:cycle-forecast` — 26 из 26.
5. В TP ничего не должно появиться: цикл — это намерение, сессии пишутся отдельно и вручную.

## Как откатить

Отката кода не требуется — цикл влияет только через свою строку.

```sql
-- мягко: цикл перестаёт действовать, история остаётся
update public.training_cycles set status = 'cancelled', updated_at = now()
where trainingpeaks_athlete_id = 5905779 and status = 'active';
```

После этого атлет возвращается на прежний путь (конверт истории) — тот самый, по которому
сегодня идут все 112. Ничего доделывать не нужно.

Жёстко (если строка заведена ошибочно и мешает): `delete from public.training_cycles where id = '<id>';`

## Чего этот документ не покрывает

- Как заводить цикл из интерфейса — интерфейса нет, только SQL.
- Что делать, когда старт переносится: `target_date` меняется руками, пересчёт длины цикла
  автоматически не происходит.
- Поведение при двух активных циклах на одного атлета — не определено и не запрещено
  ограничением в таблице.
