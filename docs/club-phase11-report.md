Ветка `feature/club-tp-execution-impl`, **застекована на `feature/club-calendar`**
(phase3→tracks→calendar→tp-execution). Флаг `CLUB_TP_EXECUTION_ENABLED` — ВЫКЛ.

## ГЛАВНЫЙ ПРИНЦИП (выдержан)
В TP создаются ТОЛЬКО НОВЫЕ пометки-события. Существующие тренировки и планы НЕ изменяются,
НЕ удаляются, НЕ переносятся — ни при каких условиях. Что делать с планом на день выходного,
решает тренер вручную.

## 11.0 РАЗВЕДКА ВОЗМОЖНОСТЕЙ TP (ДО реализации — ключевой вывод)
Через существующий write-клиент (`tp-api-client.ts`) и probe (`tp-probe-events-and-settings.ts`)
установлено ФАКТОМ:
- **TP-клиент умеет создавать ТОЛЬКО workout** (`createWorkout` → `POST /fitness/v6/athletes/{id}/workouts`,
  типы 1 swim / 2 bike / 3 run / 9 strength / 13 walk / 100 Other; `createStrengthWorkout`).
- **Отдельного типа события «Day Off» / заметки / annotation НЕТ проверенного пути.** Events-эндпоинт
  в клиенте только на ЧТЕНИЕ (`getEvents`, GET). Запись событий пробовали один раз
  (`POST .../events`, тело `{name,eventDate,eventType,description}`) — **вернулось HTTP 500** дважды
  (эндпоинт достижим, рабочего payload нет; нужен живой сетевой захват из браузера). Полагаться нельзя.
- Значит: **«выходной», «заметка», «пожелание» как ОТДЕЛЬНЫЙ тип события в TP сейчас невозможны.**

**Вывод для реализации:** каждая пометка = ОПИСАТЕЛЬНАЯ запланированная тренировка (проверенный
`create_workout`), сосуществующая с планом дня (план не трогается). Забег — бег (type 3) с дистанцией;
выходной/заметка/пожелание — тип 100 «Other» (не бег, чтобы не спутать), только заголовок+описание.
Это единственный проверенный безопасный путь; ради него НЕ трогаем непроверенный events-API.

## 11.1 ЧТО СОЗДАЁТСЯ (точно, для каждого случая) — что увидит ученик в TP
| kind | TP-действие | Тип | Что видит ученик в календаре TP |
|---|---|---|---|
| day_off | create_workout (пометка) | 100 Other | тренировка «🛌 Выходной день (заявка ученика)» на дату; **его план на день на месте** |
| preference | create_workout (пометка) | 100 Other | «🎯 Пожелание: длительная/интервальная/отдых» — описательная пометка |
| note | create_workout (пометка) | 100 Other | «📝 Заметка ученика» с текстом |
| race | create_workout | 3 Run | запланированный бег с точным названием, дистанцией; целевое время — в описании |
Заголовки единообразны и узнаваемы («заявка ученика») — сразу видно, что это из клуба.
Оговорка: create типа 100 (Other) не подтверждён end-to-end — помечен в `unresolved`, тренер проверяет
одну запись перед массовым исполнением.

## 11.2 КОНТЕКСТ В SUPABASE (основа автопланировщика)
Всё уже хранится структурно и машиночитаемо в `club_calendar_entries` (Фаза 5):
`student_id, entry_date, kind (day_off|preference|note|race), preferred_workout_type (long|intervals|rest),
note, race_*, status, source`. Интерфейс для планировщика — `getStudentDateConstraints(studentId, date)`
(`src/features/club/calendar.ts`) возвращает `{dayOff, preferredType, notes[], races[]}` по approved/applied
записям ОДНИМ запросом. **Supabase — источник истины; TP — только отображение для тренера.**

## 11.3 КОНФЛИКТЫ
Если на день выходного уже есть запланированная тренировка — НЕ трогаем. Dry-run отдельным флагом
`⚠️ КОНФЛИКТ` показывает такие случаи (ученик, дата, что запланировано), это ручной просмотр тренера.
Реализовано в `club-calendar-tp-dryrun.ts` (читает `trainingpeaks_workout_cache`, is_planned на дату).

## 11.5 ПОРЯДОК И БЕЗОПАСНОСТЬ — существующий пайплайн НЕ тронут
Планировщик `tp-execution.ts` — ЧИСТЫЙ (без Supabase/сети/очереди/исполнения): approved-запись →
`CreateWorkoutPayload`. Реальный путь (когда флаг ВКЛ, руками Игоря):
`createTrainingPeaksAction(create_workout, pending_coach)` → dry-run → подтверждение тренером →
`execute_pending` → локальный раннер → `executeByType(create_workout)` → verify(readback) → откат при провале.
Никакого нового типа действия и никакого непроверенного клиента — только проверенный `create_workout`.

**ОБЯЗАТЕЛЬНО выполнено:** dry-run по накопленным заявкам → `docs/club-tp-dryrun.md` (построчно: кто,
дата, тип, заголовок TP + конфликты + синтетические примеры каждого типа). Скрипт
`scripts/club-calendar-tp-dryrun.ts` строго READ-ONLY (читает БД, пишет только .md; в TP/очередь ничего).
Прогнан фактом против реальной БД: `club_calendar_entries` ещё не применена → 0 накопленных записей
(ожидаемо), отчёт содержит примеры форм. Реальное исполнение НЕ запускалось.

## Что НЕ сделано намеренно (и почему)
- **Не заведён отдельный тип действия и не тронут executor/`executeByType`.** Все пометки ложатся на
  ПРОВЕРЕННЫЙ `create_workout` — новый тип действия избыточен и добавил бы риск в high-risk путь.
- **Не реализован реальный enqueue→execute club→TP.** Это точка, где наряд явно отдаёт руку Игорю
  («реальное исполнение — моя рука после просмотра отчёта»). Планировщик + dry-run + идемпотентность +
  конфликты — полный «prepare»-слой; включение — отдельный осознанный шаг после ревью dry-run.
- **Не трогали events-API** (непроверен, 500). Если понадобится настоящий тип «событие»/«выходной» —
  сначала живой захват рабочего payload, затем `createEvent()`/`deleteEvent()` в клиенте (см. §1).
