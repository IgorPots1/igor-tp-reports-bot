## 1. Источник данных Coach OS и покрытие фич ядра

Основной источник — **`trainingpeaks_workout_cache`** (миграция `20260518101000_...`) + связанные:
- `trainingpeaks_students` — ростер: `id`, `student_name`, `sex ('female'|'male')`, `is_active`, `is_service_account`, `telegram_user_id/username/chat_id`. **Аватара нет** — используем инициалы/монограмму.
- `trainingpeaks_workout_laps` (FK `workout_cache_id`) — per-lap FIT: `pace_sec_per_km`, `distance_m`, `avg_hr`, `is_work`, `intensity`. Для проверки стабильности темпа в рекордах.
- `trainingpeaks_workout_derived_metrics` (уник `workout_cache_id`) — `reps_detected_count`, `rep_pace_cv`, `rep_pace_fade_pct`, `hr_decoupling_pct` и пр. **Внимание:** по шапке миграции многие скалярные колонки заполняются лишь на поздней стадии ingest — перед опорой проверять наличие.

### Единицы полей кэша (СВЕРЕНО с кодом — критично)
- **`*_time_raw` = десятичные ЧАСЫ.** Подтверждено: `formatWorkoutDuration` (`reply-draft-context.ts:760`) считает `hours*60`; `nutrition/context.ts:1161` берёт как `durationHours`. → в секунды: `hours*3600`.
- **`*_distance_raw` = метры ИЛИ км, непоследовательно.** Нормализатор `normalizeDistanceKm` (`nutrition/context.ts:549`): если `>100` → это метры, делим на 1000; иначе уже км. Используем этот же приём. (Расхождение потребителей зафиксировано — `group-workout-report-analyzer` местами трактует как метры/секунды; истина — часы+эвристика по дистанции.)
- Классификация бега — `classifyTrainingPeaksWorkoutActivity(...)` → `{ isRunning, family: 'run', confidence }` (`workout-activity-classification.ts`). Переиспользуем, берём только `isRunning`.

### Покрытие фич ядра данными Coach OS

| Фича ядра | Поля-источники | Статус |
|---|---|---|
| **Лента** — завершённые тренировки клуба | cache: `student_name`(→студент), `workout_date`, `sport_or_type_code`, `completed_distance_raw`, `completed_time_raw`, `title`, `start_time` | **(а) считается сегодня** |
| темп в ленте | `completed_time / completed_distance` (сек/км) | **(а)** |
| **Челлендж — клубный км к цели** | `sum(completed_distance_raw)` по бегу за период | **(а)** данные есть; сама ЦЕЛЬ — фикстура/конфиг **(в)** |
| **Челлендж — «красавчики недели» по % выполнения** | на студента: `count(is_completed & bег)/count(is_planned & бег)` за неделю | **(а)** |
| **Челлендж — личный вклад** | `sum(completed_distance_raw)` текущего студента | **(а)** |
| **Рекорды — 10k/21.1/42.2 (надёжные)** | завершённые беговые с `completed_distance` в полосе ±500 м + проверка стабильности темпа по `laps.pace_sec_per_km` (CV) | **(а/б)** — считается, но качество зависит от laps |
| **Рекорды — 5k (предварительный)** | то же, помечаем «предварительно» | **(а)** |
| **Клубные топы по дистанции** | лучший (min time) на дистанцию среди студентов | **(а)** |
| **Профиль (личный кабинет)** — объём нед/мес, серия, PR, место в челлендже | агрегаты по cache текущего студента | **(а)** |
| место в челлендже | ранг по % выполнения | **(а)** |
| аватар | — | **(в) нет данных** → монограмма из имени |
| реакции/лайки | — | **(в)** место заложим, данные позже |

### (а)/(б)/(в) — явное разделение
- **(а) Считается из имеющихся данных сегодня:** лента, темп, клубный км, % выполнения, личный вклад, объём нед/мес, серия дней, клубные топы, реконструкция рекордов из полос дистанции.
- **(б) Требует новых агрегатов/вьюх (делаем в сервис-слое TS, не в SQL-вьюхах):** индекс стабильности темпа для «надёжности» рекорда (CV по laps); недельная сетка планового/фактического для «красавчиков». Всё это TS-редьюсы над уже кэшированными строками — новых таблиц не нужно, кроме флага приватности.
- **(в) Невозможно без новых данных — выкидываем из v1 или фикстуры:** аватары (монограмма-замена), реакции/лайки (только место в UI), «цель челленджа» (конфиг/фикстура — цифры не выдумываем в проде, помечаем TODO), уровни/ранги/XP (модели нет).

## 2. Выгрузка новых тренировок из TP и обновление данных

Клуб НЕ инициирует обращения к TP (ученическая read-only поверхность; запись/скан TP — attended-операции локального раннера). Клуб **едет на существующем конвейере**:

1. **`tp-workouts-cache-scan.ts`** (`run-workout-cache-scan.sh`, launchd `com.igor.trainingpeaks.workout-cache-scan.plist`) — тянет тренировки из TP → upsert в `trainingpeaks_workout_cache`. Каденс — ежечасно (недавний коммит «каденс cache-scan+fit-ingest → каждый час»).
2. **`tp-fit-ingest-scan.ts`** (`run-fit-ingest-scan.sh`, `fit-ingest-scan.plist`) — FIT → `trainingpeaks_workout_laps` + `derived_metrics` (темповые детали для рекордов).
3. **`workout-cache-backfill.plist`** — историческая добивка.

**Свежесть в UI.** Читаем `getTrainingPeaksWorkoutCacheFreshness()` → `{ latestScannedAt, rowCount }`. В шапке `/m/club` показываем «обновлено N мин назад» (относительное время, гендерно-нейтрально). Так ученик видит актуальность без всякой записи в TP.

**Что новое НЕ строим:** отдельный экспорт/скан из мини-аппа. Если понадобится ручной «обновить сейчас» — это отдельная attended-кнопка у тренера (вне v1), не из ученической поверхности. Помечено в `docs/questions.md`.

**Ключевой момент для ленты «новых тренировок»:** новизна определяется по `scanned_at`/`source_updated_at` и `workout_date`; лента сортируется `workout_date desc, start_time desc`, курсор пагинации — по `(workout_date, id)`. Новые завершённые тренировки появляются в ленте автоматически после ближайшего скана (≤1 ч).

## 3. Приватность (флаг видимости на уровне ученика)

**Новая колонка (миграция-файл, НЕ применяем):** `trainingpeaks_students.club_visible boolean not null default true`.
- По умолчанию ученик **участвует** в клубной ленте/топах/челлендже.
- Возможность отключиться: `false` → ученик исключается из ленты, топов, «красавчиков», но СВОЙ личный кабинет видит всегда (это его данные).
- Плюс всегда исключаем `is_service_account = true` и `is_active = false`.

**Поля, которые НИКОГДА не показываются другим ученикам** (только агрегаты/публичный минимум):
- контакты и телега: `telegram_chat_id/user_id/username`, `telegram_context_notes`, `notes`;
- health-метрики, memory items, operational signals, context snapshots — вообще не читаем в клубе;
- `compliance_*_percent` конкретной тренировки другого ученика (это тренерская метрика) — в ленте не светим; `%` выполнения используется ТОЛЬКО агрегированно в «красавчиках»;
- точный `trainingpeaks_athlete_url`, `trainingpeaks_athlete_id`, TP workout id;
- `source_snapshot` (сырой payload TP).

**Что показывается другим (публичный минимум):** отображаемое имя (имя/первое слово `student_name`), пол — не показываем как ярлык (формулировки гендерно-нейтральные), тип тренировки, дистанция, время, темп, дата, короткая нейтральная подпись, агрегаты объёма и рекорды по дистанциям.

**Отображаемое имя.** Берём `student_name`; для публичной ленты — имя без фамилии (первое слово) как дефолт. (Решение зафиксировано в `docs/questions.md`.)

## 4. Схема экранов и роутов

Одна страница-обёртка `src/app/m/club/page.tsx` (client) с фиксированным нижним tab-bar (паттерн `/m/desk`). Вкладки:

1. **Лента** (`feed`) — хронология завершённых тренировок клуба. Карточка: монограмма+имя, тип, дистанция, время, темп, дата, короткая подпись; место под реакции (диза­блд). Бесконечный скролл (курсорная пагинация).
2. **Челлендж** (`challenge`) — клубный км к цели (прогресс-бар), «красавчики недели» (список по % выполнения, топ-3 выделены), личный вклад ученика.
3. **Рекорды** (`records`) — табы дистанций 5k(предв.)/10k/21.1/42.2: личный рекорд (время/темп/дата, флаг надёжности) + рядом клубные топы по дистанции.
4. **Профиль / личный кабинет** (`profile`) — карточка ученика: объём за неделю/месяц, серия, личные рекорды, место в челлендже. Богатый экран с реальными данными — акцентный.

Все данные грузятся лениво при первом открытии вкладки (паттерн `/m/desk`: `useEffect` guard на `status==='idle'`).

### Роуты API (`/api/m/club/*`, `runtime="nodejs"`)
Каждый: гейт `isClubEnabled()` (`MINIAPP_ENABLED==='true' && CLUB_ENABLED==='true'`) → `resolveMiniAppStudent({ initData })` → сервис-слой → `jsonResponse`.

| Роут | Метод | Тело | Ответ (view) |
|---|---|---|---|
| `/api/m/club/feed` | POST | `{ initData, cursor? }` | `{ ok, view: { items: FeedItem[], nextCursor, freshness } }` |
| `/api/m/club/challenge` | POST | `{ initData }` | `{ ok, view: { clubKm, goalKm, goalIsFixture, topPerformers[], personal } }` |
| `/api/m/club/records` | POST | `{ initData, distance? }` | `{ ok, view: { personal: RecordByDistance[], clubTops: {distance, rows[]}[] } }` |
| `/api/m/club/profile` | POST | `{ initData }` | `{ ok, view: { name, weekKm, monthKm, streakDays, records[], challengeRank } }` |

Контракты типов — в `src/features/club/types.ts`. Сервис-функции — `src/features/club/service.ts` (тонкие роуты, вся логика в сервисе, как в `/m/desk`).

## 5. Логика вычислений (воспроизводим на данных Coach OS)

- **Темп** = `durationSeconds / distanceKm` (сек/км), формат `mm:ss/км`. Только для бега и при `distanceKm>0`.
- **Клубный км** = Σ `normalizeDistanceKm(completed_distance_raw)` по беговым `is_completed` за период (неделя ISO, TZ Europe/Belgrade как в проекте — сверить с `BELGRADE_TIMEZONE`).
- **«Красавчики недели» (по % выполнения, НЕ по скорости/км):** на студента за неделю `planned = count(is_planned & бег)`, `done = count(is_completed & бег)`, `pct = planned>0 ? min(done/planned,1) : (done>0?1:0)`. Ранг по `pct desc, done desc`. Топ-3 выделяем. (Требует ≥1 планового бега в неделю у студента, иначе «нет плана» — показываем отдельной пометкой, не 0%.)
- **Личный вклад** = Σ дистанции текущего студента за период; доля от клубного км.
- **Рекорды по дистанции:** беговые `is_completed`; `d = normalizeDistanceKm(completed_distance_raw)`; для цели T∈{5,10,21.097,42.195} км берём тренировки с `|d - T| ≤ 0.5 км`. PR = min `durationSeconds`. **Надёжность:** `reliable` если (есть laps с `pace_sec_per_km` и CV темпа ≤ порога, напр. 0.08) ИЛИ дистанция ровно в узкой полосе (±0.15 км). 5k всегда помечаем «предварительно». Клубные топы — min по студентам на дистанцию, сорт `duration asc`.
- **Объём нед/мес** — Σ дистанции за ISO-неделю / календарный месяц.
- **Серия (streak)** — число последовательных дней (от сегодня назад) с ≥1 завершённой беговой; разрыв обрывает.

Пороги (CV темпа, полоса ±0.5, ±0.15) — вынести в константы `src/features/club/constants.ts` с комментариями; при нехватке laps честно помечать «предварительно», цифры не выдумывать.
