# Регистрация в /m/club — фактическое поведение и явная привязка

Дата: 2026-07-25. Коммит 3.

## Что делает общий резолвер (`resolveMiniAppStudent`) — факт

**Молчаливая авто-привязка (trust-on-first-use).** При первом открытии мини-аппа резолвер сам привязывает `telegram_user_id` к строке ученика по `start_param` (row id ученика, зашитый в подписанную ссылку от тренера), без экрана подтверждения. Гарды, которые уже есть:
- **coach_account** — личный аккаунт тренера привязывать/показывать нельзя (403).
- **wrong_target** — если аккаунт уже привязан к ДРУГОму ученику, а ссылка на иного — отказ (403).
- **collision** — если ученик уже занят другим `user.id` или наоборот — отказ (409), тренер получает уведомление.
- Пишется атомарно ТОЛЬКО колонка `telegram_user_id` (update ... where telegram_user_id is null).

Это поведение используется ученическим питанием `/m/n` и **здесь НЕ меняется** (чтобы не задеть /m/n).

## Спека v3 блок 2.1

В репозитории её нет (проверено: `docs/specs/` отсутствует, поиск по «2.1 / подтверждение / registration» ничего не дал). Поэтому точный текст/поток экрана подтверждения из наряда v3 воспроизвести дословно нельзя. Реализована **разумная явная привязка, клуб-скоуп**, не трогая общий резолвер.

## Что сделано в клубе — явная привязка (замена молчаливой)

- **Данные-роуты клуба НЕ привязывают.** `resolveClubStudent` (в `miniapp-guard.ts`) — теперь **чистое чтение (peek)**: валидирует initData, отсекает тренера, и
  - если аккаунт уже привязан → отдаёт ученика;
  - если нет → возвращает `needs_confirm` с ИМЕНЕМ кандидата (читает `student_name` по row id из `start_param`, БЕЗ записи), либо `needs_link`, если ссылки нет.
- **Экран подтверждения.** Клиент на `needs_confirm` показывает «Это ты? → {Имя}» и кнопку «Да, это я». До подтверждения никакие данные не грузятся и привязка не происходит.
- **Единственная точка привязки — `POST /api/m/club/confirm-link`.** Вызывается только после явного тапа; делегирует фактическую привязку общему `resolveMiniAppStudent` (со всеми его гардами). Ничего никому не шлёт.

Итого: в клубе нет молчаливого бинда на форварднутой/расшаренной ссылке — ученик сначала видит, к какому имени привяжется, и подтверждает.

## Откат ошибочной привязки (тренерская отвязка ещё не реализована)

Привязка пишет ТОЛЬКО `trainingpeaks_students.telegram_user_id`. Чтобы отвязать ошибочно привязанный аккаунт — обнулить эту колонку (в Supabase SQL editor, прод):

```sql
-- 1. Найти, к кому привязан подозрительный user.id
select id, student_name, telegram_user_id, telegram_username
from public.trainingpeaks_students
where telegram_user_id = <WRONG_TELEGRAM_USER_ID>;

-- 2. Отвязать (по user.id — снимет со всех, куда он ошибочно попал)
update public.trainingpeaks_students
set telegram_user_id = null
where telegram_user_id = <WRONG_TELEGRAM_USER_ID>;

-- или точечно по конкретному ученику:
update public.trainingpeaks_students
set telegram_user_id = null
where id = '<STUDENT_ROW_ID>';
```

После отвязки ученик при следующем открытии клуба снова увидит экран подтверждения и сможет привязаться заново (к правильной строке — по своей ссылке от тренера).
