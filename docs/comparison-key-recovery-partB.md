# comparison_key: диагноз + восстановление легаси (Часть B — ПОДГОТОВКА, не запускать)

## Причина (не та, что предполагалась)
НЕ неполный backfill и НЕ баг парсера ключа. Легаси `summaryOnly`: до **2026-07-09**
(коммит `05c0f9d`) скан кэша (`tp-workouts-cache-scan.ts`) выбрасывал любую структуру
плана длиннее **2000 байт** (`if (serialized.length <= 2000)`), сохраняя только сводку
`{summaryOnly:true, serializedLength, nodeCount, …}`. Структуры интервалок с целевыми
зонами по шагам легко перевешивают 2 КБ → **полная структура удалена** и в снапшоте не
восстанавливается (проверено: единственное поле `source_snapshot.structure` = сводка,
сырого поля структуры нет). `computeComparisonKey` корректно отдаёт null — парсить нечего.
Порог 2026-07-09 подняли до 100 000; новые интервалки ключуются нормально.

Backfill текущим парсером изменит **0 строк** (данных нет). Единственный путь к настоящему
ключу — **переснять структуру плана из TP** (уже с порогом 100 КБ), затем прогнать
существующий idempotent-backfill.

## Часть A (сделано в коде — фикс симптома, без TP)
`session-type.ts`: run без `comparison_key`, но с `reps_detected_count >= 3` теперь
классифицируется как **interval** (фидбек разбирает дугой серии, а не хвалит «ровную
пробежку»). Порог 3 отсекает темповые «2 блока». Вето: явный лёгкий/восстановительный
титул БЕЗ паттерна «N×M» → остаётся easy (гасит ложные reps эвристики на лёгких).
Живьём: 805 тренировок easy/длительная → interval, истинных регрессов 0.
База сравнения по этим строкам пока молчит (нет ключа для группировки) — мягкая деградация.

## Часть B — восстановление ключей (катает Игорь, когда будет окно)
**554** summaryOnly-интервалки (key NULL, reps>=2, структура утеряна) у **60** учеников,
даты **2025-06-03 .. 2026-05-20**. Это чтение из TP — как с health-сканом: осторожно с
браузерным профилем, если служба запущена. B не блокирует мост: разбор работает и без ключа.

### Команды (из папки с main; НЕ запускаю сам)
1. Переснять структуру плана из TP по затронутому окну (можно по-ученически из таблицы
   ниже, либо разом по всем активным за диапазон):
   ```
   # разом по всем активным за диапазон (проще, но тяжелее по TP):
   npm run tp-workouts-cache-scan -- --all-active --from=2025-06-03 --to=2026-05-20
   # либо точечно по ученику (легче на TP):
   npm run tp-workouts-cache-scan -- --student="Anna Plotnitskaya" --from=2025-06-03 --to=2026-05-19
   ```
2. После рескана — прогнать существующий idempotent-backfill (dry-run → затем --apply):
   ```
   npx tsx tools/trainingpeaks-export/scripts/tp-comparison-key-backfill.ts            # dry-run, покажет распределение
   npx tsx tools/trainingpeaks-export/scripts/tp-comparison-key-backfill.ts --apply     # запись ключей
   ```
3. Проверка: `comparison_key` у переснятых интервалок стал не-NULL; они получают
   confidence=high (keyed) вместо medium (reps-fallback), и база сравнения начинает
   группировать их с историей.

Оговорка: часть из 554 после рескана всё равно может остаться null, если структура
плана в TP реально плоская (шаги без repeat-обёртки, открытая длина) — это корректный
null, не баг. Ожидаемый потолок восстановления ≈ 554.
